## 1. 目标与范围

LexiFlow 的第一入口是 YouTube 英语字幕辅助。英文字幕必须先于任何后端或模型结果显示；系统只给用户可能不熟悉的单词、短语、术语提供简短、结合语境的中文提示。长期核心资产是跨设备共享、可解释、可重算的个人词汇档案（`Vocabulary Profile`）。

阶段 1 固定以下架构性质：

- 后端采用模块化单体，在一个代码库内以限界上下文和可检查依赖隔离业务。
- `api` 与 `worker` 是同一应用的两个运行入口，共享领域与应用层模块，但具有不同延迟和故障边界。
- Chrome 扩展是薄客户端。它负责字幕接入、播放上下文、英文优先渲染、增量提示注释合并、行为采集与 L1 缓存；后端持有权威用户状态。
- 提示编排使用确定性快速通道和模型语义慢速通道。模型不可阻塞英文字幕，也不可成为所有字幕的必经路径。
- 学习归约先保存事实事件，再产生可解释的个人词汇档案投影；不把整个系统建设为事件溯源。
- PostgreSQL 保存权威事实和可恢复状态；Redis 与浏览器缓存均可丢弃、可重建，不能决定正确性。

本阶段不决定客户端与后端的增量传输方式、表结构、消息格式或模型供应商。Java 25 与 Spring Boot组合根边界已固定；业务领域类型与具体适配器仍留给后续阶段。

## 2. 架构原则

### 2.1 产品原则

1. **英文优先**：字幕首屏只依赖播放器和扩展本地状态。
2. **选择性帮助**：规则决定是否需要帮助，模型决定当前语境下帮助的内容。
3. **可安全缺失**：无缓存、模型超时、工作进程不可用时，用户仍可正常看英文字幕。
4. **服务端拥有的个人档案**：多个设备共享后端的个人词汇档案；客户端缓存只是带版本的副本。
5. **事实先于分数**：行为事实不可被熟悉度分数替代；分数必须能追溯到规则版本和输入事件。
6. **来源无关核心**：YouTube 只是一种内容来源，不能渗入词汇、学习和语义核心模型。

### 2.2 工程原则

以下约束沿用参考仓库 `feipi-session-browser-java` 已验证的做法：

- 领域不依赖网页框架、数据库驱动、缓存客户端、序列化实现或模型 SDK。
- 应用层只面向公开 API 与出站端口编排，不直接引用具体适配器。
- 具体适配器只能由组合根装配，业务模块不能反向依赖启动入口。
- 依赖白名单和禁止导入必须成为机器可读的架构清单，并由架构测试执行。
- Harness 只保存静态、机器可读的负责人；运行结果进入不可覆盖的运行证据，不把临时状态写回规则文件。
- Gate 显式运行；未运行、跳过或不可用均不能报告为 `PASS`。
- 大任务先按可验收功能拆分，再将同负责人、同合同/写入边界的连续任务聚合为工作包。Qoder 与 Codex 均使用稳定 `work_package_id`、精确 `task_ids[]` 和逐任务结果；调用者与运行器的字段、任务规模和回调约束以 [agent-policy.manifest.yaml](../../../harness/agent-policy.manifest.yaml) 为准。并行写范围不得重叠，主代理独立验收。

## 3. 假设

| ID | 假设 | 架构影响 | 需要验证的时机 |
|---|---|---|---|
| A-01 | 首个版本允许先服务单个用户，但所有业务数据从第一天带租户/用户边界。 | 后续开放多用户时无需重写领域。 | 身份/API 设计前 |
| A-02 | Chrome 扩展能获得至少当前字幕文本、时间范围和视频身份；上一句/下一句可能不完整。 | 内容上下文必须允许缺项和乱序，不能假设完整转写。 | 扩展探索验证 |
| A-03 | 网络、字幕和模型都可能间歇不可用。 | 英文渲染本地完成；增强结果可缺失、超时或晚到。 | 首个端到端原型 |
| A-04 | 中文是首个提示目标语言，未来可能扩展其他目标语言。 | 提示注释语义中保留目标语言概念，核心规则不写死中文。 | 数据/API 设计前 |
| A-05 | 客户端重试和离线补传会造成至少一次投递。 | 学习归约接收、异步作业和结果合并都必须幂等。 | 数据/API 设计前 |
| A-06 | 大多数隐式行为不要求即时改变下一帧字幕。 | 普通学习归约投影可异步；显式“认识/不认识”需要读己之写。 | 学习归约交互评审 |
| A-07 | 初期吞吐不支持引入专用消息平台的成本。 | 使用 PostgreSQL 持久化的事务发件箱/作业边界驱动工作进程；Redis 不承担唯一队列。 | 压测显示瓶颈时复审 |
| A-08 | 语义提供者的延迟、成本和可用性差异很大。 | 语义供应商必须可路由、可超时、可观测且可替换。 | 提示编排详细设计前 |

## 9. 同步与异步边界

| 操作 | 边界 | 原因 | 超时/失败语义 |
|---|---|---|---|
| 英文字幕渲染 | 客户端同步 | 核心体验不能依赖网络。 | 永远不被提示注释失败阻塞。 |
| L1 缓存读取与有效性检查 | 客户端同步 | 低延迟；只读副本。 | 未命中即继续显示英文。 |
| 认证、授权、输入验证 | API 同步 | 在接受数据或返回个人状态前必须完成。 | 明确拒绝，不提交异步工作。 |
| 内容上下文归一化 | API 同步且有界 | 快速提示编排必需；不拉取完整视频。 | 使用缺项上下文或返回可恢复错误。 |
| 词库/个人档案/缓存查询 | API 同步且并行 | 提示需求的必要输入。 | 缓存未命中可回源；超预算则空提示注释降级。 |
| 候选与提示需求规则 | API 同步 | 确定性、低延迟、可测试。 | 失败不调用模型兜底；返回英文安全降级。 |
| 已缓存语义结果合并 | API 同步 | 无外部等待即可提高质量。 | 版本不兼容则忽略。 |
| 语义工作持久交接 | API 同步到提交/失败结论 | 客户端只能等待真实存在的异步工作。 | 提交后才返回待处理；入队失败返回快速结果 + 无待处理任务。 |
| 语义供应商缓存未命中 | 工作进程异步 | 隔离长尾延迟、成本与供应商故障。 | 截止时间、有限重试、可审计终态；不阻塞字幕。 |
| 持久化提示注释结果写入 | 工作进程经提示编排同步到提交 | 增量投递必须有提示编排领域拥有的权威结果。 | 未提交不声明已生成/已完成，不触发投递。 |
| 增量客户端投递 | `Client Delivery / Sync` 异步 | 与原 API 请求生命周期解耦，支持重连和陈旧检查。 | 投递失败可重试；不等于已显示。 |
| 当前/下一字幕预取 | 工作进程异步 | 用播放前瞻隐藏模型延迟。 | 晚到可丢弃；不改变权威状态。 |
| 学习归约事件持久化接收 | API 同步到提交 | 客户端需要知道事实是否安全落地。 | 未提交不确认；允许幂等重试。 |
| 显式 known/unknown 投影 | 与接收同一 API 用例，同步到档案版本或待处理结论 | 满足强意图读己之写，同时保持单次响应。 | 成功响应含版本；失败响应只声明事件已接受 + 投影待处理，工作进程修复。 |
| 隐式行为投影 | 工作进程异步 | 可批处理，避免交互延迟放大。 | 至少一次 + 幂等；最终一致。 |
| 重放、补录、分析 | 工作进程异步 | 非交互型、资源较重。 | 独立运行证据，不覆盖旧投影。 |

所有 API 等待都有明确截止时间。外部供应商、工作进程和 Redis 均不得无限占用 API 请求；工作进程不回调原始请求对象。是否采用轮询、SSE 或 WebSocket 只影响 `Client Delivery / Sync` 的传输适配器，不改变持久交接、提示编排结果归属与增量结果语义。

## 10. 数据、缓存与一致性边界

<a id="101-source-of-truth"></a>

### 10.1 事实来源

- PostgreSQL：用户身份、内容的权威归一化记录、词库权威数据、学习归约事件、个人词汇档案投影、提示编排领域拥有的提示注释持久化结果、异步交接和投递状态。
- Redis：个人档案/词库/语义热点缓存、去抖和短期协调。删除全部 Redis 数据后，系统行为可以变慢但不能产生不同的权威结论。
- 扩展本地存储：最近字幕/提示注释/个人档案版本的 L1 缓存与尚未确认的行为事件。它不能覆盖后端个人档案。

这只是负责人与一致性定义；表、索引和迁移在阶段 2 设计。

### 10.2 一致性模型

- 用户显式纠正：同一会话读己之写。
- 隐式学习归约：最终一致，档案版本单调前进。
- 异步投递：至少一次；提示编排结果与客户端投递状态分属不同负责人，消费方、投递和客户端合并均幂等。
- 语义结果：允许重复计算；以语境/策略版本判定可复用性。
- 缓存：版本化的或显式失效；任何缓存命中都不能绕过用户归属。
- 迟到结果：只能补充仍匹配的字幕，不能回滚更新的个人档案或提示注释修订号。

## 11. 失败隔离与可观察性

### 11.1 失败隔离

| 故障 | 必须保留的能力 | 降级结果 |
|---|---|---|
| API/网络不可达 | YouTube 原英文字幕、L1 命中、行为本地排队。 | 无新提示注释；恢复后补传事件。 |
| Redis 不可用 | PostgreSQL 权威读写、英文字幕。 | 延迟上升，禁止返回错误权威状态。 |
| 工作进程不可用 | 快速提示编排、学习归约事件接收。 | 语义和隐式个人档案更新待处理。 |
| 语义交接入队失败 | 英文字幕、已有快速提示注释。 | 快速响应明确无待处理任务；不得承诺稍后会有慢速结果。 |
| 语义供应商超时/限流 | 快速提示注释、英文字幕。 | 当前语义提示缺失；可由预取或缓存改善。 |
| PostgreSQL 不可用 | 客户端英文字幕与已有 L1。 | 不确认事件、不伪造个人档案/提示注释写入成功。 |
| 字幕上下文缺失 | 当前英文字幕。 | 降低或放弃语境提示，不猜测。 |

### 11.2 观察边界

一次字幕工作流协调和一次行为工作流协调都必须拥有端到端关联，并记录：快速/慢速通道、缓存层级、规则/个人档案/模型版本、各阶段延迟、降级原因和最终状态。日志默认不记录完整字幕、模型输入、认证材料和个人词汇历史；诊断需要内容时使用显式脱敏采样。

延迟指标至少按 `client render`、`api fast path`、`semantic queue wait`、`provider call`、`incremental delivery` 分段统计 P50/P95/P99。不能用平均延迟掩盖字幕场景的长尾。具体 SLO 数值在端到端探索验证后确认；在此之前的硬约束是供应商延迟不计入快速路径，英文首屏不计入后端依赖。

## 12. 架构约束

以下规则使用“必须”时，应在实现阶段转成架构测试、合同测试或 Gate：

1. 领域代码不得导入网页、数据库、Redis、序列化、浏览器或模型供应商实现。
2. 应用层和入站适配器不得访问具体持久化/供应商适配器。
3. 只有引导模块可装配具体适配器；引导不得实现领域判断。
4. 模块只能使用其他上下文的公开 API；不得跨上下文读取对方表或内部包。
5. 模块依赖图必须无环，并与机器可读允许列表一致。
6. YouTube 专有类型不得越过来源适配器进入 `content-api` 或其他核心模块。
7. 个人词汇档案的写入只能来自受信应用层命令或学习归约证据；客户端不得提交权威分数。
8. 学习归约事件确认必须晚于持久提交；显式行为的单次最终响应还必须晚于同步投影的成功或待处理结论。重复事件/作业/证据不改变最终结果。
9. 语义供应商调用不得进入 API 快速路径的必需依赖。
10. 提示编排必须在模型结果前后都执行展示策略；模型不能自行绕过已掌握词项、数量和信心门槛。
11. PostgreSQL 是正确性负责人；清空 Redis 或 L1 后系统必须能够恢复同一权威状态。
12. 外部枚举和值必须有稳定传输值，不依赖语言枚举的名称或顺序。
13. `pending` 必须有已提交的持久交接；入队失败必须无待处理任务降级。工作进程经提示编排写入持久化结果，`Client Delivery / Sync` 才负责关联投递。
14. 工作进程不直接回调原 API 请求对象；异步结果投递必须与原请求生命周期解耦。
15. 结果携带足够版本/身份，使客户端能拒绝陈旧或跨字幕合并；已生成/已投递不等于已显示/已点击。
16. 所有异步消费以至少一次设计并幂等；不得以“通常只投递一次”为正确性前提。
17. 共享 harness/architecture 清单是规则负责人；不同代理客户端配置只做入口，不复制规则正文。

## 13. 必须、建议与后续演进

<a id="must-have"></a>

### 必须具备

- 上述七个限界上下文、公开边界和无环依赖。
- 英文优先渲染；快速路径不等待外部模型。
- PostgreSQL 权威状态、Redis/L1 可丢弃缓存语义。
- 来源无关内容上下文和 YouTube 适配器隔离。
- 不可变学习归约事实、幂等接收、可解释档案投影。
- 显式 known/unknown 的读己之写；隐式行为最终一致。
- 供应商无关语义端口、截止时间、错误和置信语义。
- `api`/`worker` 两个组合根与持久化异步交接。
- `client-delivery-sync` 应用模块；提示编排结果与投递状态的不同负责人。
- 提交前声称待处理禁止、入队失败无待处理任务降级、显式行为单次最终 ACK。
- 仅实际显示的提示注释产生 `HintDisplayed`；已生成/已投递/已显示/已点击四级语义。
- 关联/版本/幂等性，以及可执行架构/合同/用户旅程检查。
- 隐私边界：认证数据、完整字幕和个人历史不进入默认日志。

<a id="should-have"></a>

### 建议具备

- 上一句/当前句/下一句的有界上下文窗口与下一句预取。
- 语义、词库、个人档案的分层缓存与可观测命中/未命中。
- 个人档案/评分/模型/规则版本和重放对比能力。
- 提示注释数量、置信度和解释级别的策略预算。
- 工作进程优先级、背压、死信/人工诊断状态。
- 可替换模拟实现供应商/模拟实现时钟/模拟实现存储的确定性测试接口。
- 架构清单、统一 Gate 入口和不可覆盖的运行证据。

<a id="can-evolve-later"></a>

### 后续演进

- 概率化 `P(user knows term | context)` 和更复杂学习归约模型。
- 网页、应用、PDF、播客与其他视频网站来源适配器。
- 更强的本地 NLP、嵌入或向量数据库；只有检索工作负载证明必要时引入。
- 多供应商动态成本路由、A/B 实验和个性化解释深度。
- 专用消息平台、独立微服务、Kubernetes；只有吞吐、故障隔离或团队归属有数据支撑时拆分。
- 跨设备实时个人档案 push；初期由服务端版本自然收敛。

## 14. 可执行验收合同

阶段 1 没有产品实现，因此此处定义后续 Gate 必须执行的行为合同，而不是声称当前已通过。每个验收 ID 都能成为独立任务和固定测试样例；结果只允许 `PASS`、`FAIL`、`BLOCKED`，必需检查未运行或跳过不得记为 `PASS`。

| ID | 测试样例 / 动作 | 可观察结果 | Gate 类型 |
|---|---|---|---|
| ARCH-001 | 扫描所有生产模块的项目依赖。 | 每条依赖都在允许列表，图无环，内部包无跨上下文导入。 | 架构 |
| ARCH-002 | 扫描领域/应用字节码或源码导入。 | 不含网页、JDBC/数据库、Redis、供应商 SDK、具体适配器等禁止导入。 | 架构 |
| ARCH-003 | 启动两个组合根并检查模块归属。 | `api`/`worker` 只装配；共享业务行为来自同一应用/领域实现。 | 架构 |
| FLOW-001 | 语义模拟实现延迟远超 API 截止时间，提交一条新字幕。 | 扩展先显示英文；API 快速结果在自身预算内完成；供应商不阻塞快速路径。 | 旅程 + 时延 |
| FLOW-002 | 个人档案表示用户已掌握 `materially`。 | 候选可被检测，但最终快速/慢速提示注释都不展示该词项。 | 领域合同 |
| FLOW-003 | 用合法、区块链两组上下文处理 `settlement`。 | 提示编排使用不同语境化含义，全局词库不被覆盖成单一永久义。 | 领域合同 |
| FLOW-004 | 慢速提示注释在客户端切换字幕后到达。 | 客户端根据身份/修订号拒绝陈旧结果，不污染当前字幕。 | 客户端合同 |
| FLOW-005 | 清空 Redis 与 L1 后重放同一权威数据。 | 结果可能更慢，但用户归属、个人档案和已持久化结果保持一致。 | 韧性 |
| FLOW-006 | 持久交接提交成功与入队失败各提交一次语义未命中。 | 成功场景快速结果才含待处理；失败场景只有快速结果 + 无待处理任务，客户端不等待虚构工作。 | 事务 + 旅程 |
| FLOW-007 | 工作进程完成语义工作，原 API 请求已结束。 | 提示编排持久化持久化结果；客户端投递与同步关联投递，工作进程不直接回原请求。 | 归属 + 旅程 |
| LEARN-001 | 同一行为事件重复提交、同一作业重复投递。 | 事件只形成一次有效证据，个人档案不重复累计。 | 合同 |
| LEARN-002 | 提交 `WordMarkedKnown` 后立刻请求下一字幕，并注入一次投影失败。 | 成功仅有一次最终响应且含新档案版本；失败仅有一次事件已接受 + 投影待处理响应，不虚构读己之写。 | 旅程 |
| LEARN-003 | 提交提示显示/点击/重放等隐式事件。 | API 在持久提交后确认；工作进程最终更新个人档案，API 不等待投影。 | 旅程 |
| LEARN-004 | 对固定事件集用同一评分版本重放两次。 | 得到等价个人档案；换新版本时旧投影与原始事件仍可审计。 | 重放合同 |
| LEARN-005 | 提示注释分别生成未送达、送达但陈旧、写入 L1 未显示、实际显示并点击。 | 只有实际可见渲染产生 `HintDisplayed`，只有引用已显示结果的交互产生有效 `HintClicked`；前几种不增加显示接触次数。 | 客户端 + 学习归约合同 |
| SOURCE-001 | 内容输入缺少下一句或乱序。 | 当前英文和可用快速路径正常；系统降低信心或不提示，不猜造上下文。 | 领域合同 |
| TENANT-001 | 设备 A 更新个人档案，设备 B 发起提示编排；另一个用户请求相同词项。 | A/B 共享最新服务端用户状态；不同用户结果和缓存隔离。 | 安全旅程 |
| FAIL-001 | 分别注入供应商、工作进程、Redis、PostgreSQL 故障。 | 降级与第 11 节一致；所有“已接受/已完成”状态都由真实持久化证据支撑。 | 失败注入 |
| OBS-001 | 跑完整快速 + 慢速 + 学习归约旅程。 | 关联可串联各阶段，能计算分段 P95/P99，默认日志无完整字幕和敏感数据。 | 可观测性 |

实现后的统一增量 Gate 至少选择受变更影响的架构、合同和旅程验收；跨模块或发布候选再运行完整 Gate。具体命令由仓库 Harness 在工程初始化时声明为唯一入口。

<a id="15-面向大规模-sub-agent-的工作分解边界"></a>

## 15. 面向大规模子代理的工作分解边界

后续数百个子功能应沿稳定负责人拆分，而不是让代理自行创造跨模块捷径：

1. 一级按阶段与限界上下文建工作流，例如 `content-normalization`、`learning-intake`、`semantic-routing`。
2. 二级按一个公开能力或一个验收 ID 拆原子任务；实现与直接关联测试一起交付。原子任务用于 DAG 与收据，不直接等于一次代理会话。
3. 接口变更先由独立合同任务固定公开 API 和验收测试样例，再并行适配器/实现；集成串行。
4. 实际委派使用工作包，原子任务保留独立验收身份；Codex 与 Qoder 均绑定稳定 `work_package_id` 与精确有序 `task_ids[]`。模型、规模、范围与并发限制统一见 `harness/agent-policy.manifest.yaml`，不得把原子任务直接等同于一次代理会话。
5. 并行任务的写范围不得重叠；共享清单、依赖清单、迁移顺序和组合根由单负责人串行修改。
6. 每个原子任务分别保留结果证据；代理工作包的 `PASS` 只是输入证据，主代理必须检查必要差异、范围、声明命令、Gate 原始结果和跨模块效果。
7. 工作包优先靠精简完成回调；主会话不做高频轮询。首次兜底检查不得早于五分钟，后续不得频于十分钟，并应使用非 LLM 守护检查器或单次有界检查。

这一分解合同让边界完整的实现/复核工作包可以安全交给 Qoder 或 Codex 子代理；不足两小时的小修改与检查由主代理直接完成，跨上下文决策、冲突处理和最终验收仍保留给主代理。

<a id="16-phase-1-评审出口"></a>

## 16. 阶段 1 评审出口

进入阶段 2 前应明确接受或修改以下方向：

- 七个限界上下文的负责人是否完整；
- 模块化单体 + `api`/`worker` 两入口是否接受；
- 语义缓存未命中全部离开快速路径是否接受；
- 显式行为同步投影、隐式行为异步投影的一致性分层是否接受；
- PostgreSQL 持久交接作为初期异步边界是否接受；
- YouTube 专有的逻辑仅位于客户端/来源适配器是否接受。

决策理由、替代方案与复审触发器见 [decisions.md](../decisions.md)。

语义能力/结果、缓存正确性与隐私、信任边界、遥测脱敏和来源适配器符合性的细化约束见 [阶段 1 横切架构合同](README.md)。这些合同保持 `Proposed`，须经独立复核和正式 Gate 收据后才能满足对应目录任务；文档存在本身不等于任务 `PASS`。
