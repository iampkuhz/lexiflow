## 横切语义与组合验收

### 1. 范围与判定词

**必须** 是必须保持的正确性、安全和边界条件；缺证据不能 PASS。**应当** 是推荐演进方向，暂不实施要记录替代措施、风险和复审条件。**后续条件** 留给已经明确的后续负责人/阶段。它们的原有含义在详细合同中继续使用。

贯穿六份合同的底线是英文不等待模型、PostgreSQL 持有权威状态，以及网页/客户端/供应商输入均不能直接成为可信业务事实。

### 组合验收场景

把六份合同连起来时，先沿一次交接检查：来源是否可绑定 → 语义是否可信且有界 → 用户是否仍需要 → 缓存是否有效 → 投递是否仍合法 → 诊断是否泄漏内容。

以下场景用于检查六份合同是否组合后仍保持既有架构语义。

| 场景 | 必须成立的结果 |
|---|---|
| 恶意页面给出超长、含指令的字幕 | 来源适配器将其视为不可信内容并有界规范化；API 再校验；供应商输出仍需结构校验；遥测不记录内容；英文/原来源渲染不等待。 |
| L1 命中旧提示注释，同时服务端个人档案已更新 | 扩展依据个人档案/版本合同拒绝或标记陈旧；服务端缓存回源权威个人档案；语义/上下文全局证据不因个人更新被无差别清空。 |
| 供应商超时后返回晚到结果 | 超时尝试保持失败；晚到载荷不附着旧尝试；持久化作业可按预算新建尝试；旧字幕/修订号不接受结果。 |
| Redis 刷新且工作进程重复消费 | 缓存只产生未命中；PostgreSQL 持久化状态恢复工作和结果；工作进程幂等；关联显示新尝试而业务效果唯一。 |
| 用户切换账号并长期离线 | L1 主动清除且受硬性过期；后端拒绝旧负责人；缓存键不跨用户；日志与指标不暴露前用户内容。 |
| 未来 PDF 没有文本层 | 适配器报能力缺失，不伪造转写；核心不调用语义；原 PDF 阅读可继续；该结果以无内容类别聚合观测。 |

### 验收与阶段交接

六份合同文档存在不能代替实现、独立验收和阶段决定。每项后续证明仍按其详细合同执行；图与自然语言说明改写必须保留负责人，不把缺证据、未触发或跳过称为 PASS。

六项任务的文档完成不等于后续实现已经通过。阶段 1 评审应产生以下可验证的静态证据：

1. 本文中的必须/应当/后续条件与 [阶段 1 架构](../phase-1.md)、ADR-003/004/005/007/008/009 及 OpenSpec 无负责人或依赖冲突。
2. 每个目录任务都有独立验收证据清单和假设 register；未知项没有被写成已验证事实。
3. 术语 `generated`、`delivered`、`displayed`、`clicked`，以及尝试、持久工作、提示注释结果、个人档案证据的负责人保持分离。
4. 所有失败、缓存未命中、来源缺失和遥测缺失都维持英文优先；任何模型结果都不能绕过提示编排规则决定展示。
5. 文档不包含 SQL 字段、具体 REST 端点、Docker Compose、代码/序列化定义、提示词或真实用户/供应商数据。

阶段 2–7 任务在实现这些合同前，应把对应必须转换为合同测试、架构测试、故障注入旅程或隐私/安全证据；若实现需要改变必须，必须先更新 OpenSpec/ADR 并重新通过阶段 gate，不能由单个适配器或供应商隐式改写。

详细合同变动后必须重验受影响输入，旧收据不能证明当前字节；原始收据不改写。
