# 1. LexiFlow 架构总览

LexiFlow 在 YouTube 英文字幕上提供通用、低打扰的中文语境提示。英文先显示；共享规则决定是否提示；模型提供语境含义。产品不维护账号、个人档案、学习行为或跨设备同步。

## 1.2. 系统边界

Chrome 扩展拥有当前视频、字幕、叠加层和本机缓存；服务端拥有共享词库、提示规则、异步工作和结果；外部供应商只返回不可信语义证据。PostgreSQL 是服务端事实存储，Redis 与浏览器缓存可重建。

扩展只发送当前片段和最小必要上下文。服务端不接收账号、设备注册、观看历史、个人熟悉度或行为反馈，不由这些数据影响提示决定。

## 1.3. 主链路

1. 扩展立即显示英文字幕。
2. 扩展/来源适配器将字幕归一为 Enrichment 的 `CaptionContext` 输入；Enrichment 从 Lexicon 找到候选，并以共享规则决定是否提示。
3. 已有可靠语义证据时返回快速提示；缺口只有在 durable handoff 已提交后才标为 `pending`。
4. worker 通过语义能力取得证据，Enrichment 重新核对内容修订号和规则版本后持久化结果。
5. 扩展仅合并匹配当前字幕和修订号的结果；晚到或过期结果丢弃。

完整失败分支见[字幕提示流程](flows.md)。规则与模型的职责、供应商输入边界见[语义合同](semantic-contract.md)。

## 1.4. 模块与运行入口

Lexicon 与 Enrichment 是两个业务领域：`CaptionContext` 是 Enrichment 输入合同，语义能力归 Enrichment，供应商集成归位于最外层的 `platform:infrastructure`。`workflow` 协调用例，`api` 和 `worker` 负责装配。模块职责与禁止依赖见[模块边界](boundaries.md)。

## 1.5. 架构底线

| 保证 | 含义 |
|---|---|
| 英文独立显示 | 网络、模型、工作进程失败不阻断观看。 |
| 规则与模型分离 | 规则决定是否提示，模型只解释语境。 |
| 事实与副本分离 | PostgreSQL 为服务端事实，Redis/L1 只优化读取。 |
| 无个人状态 | 账号、多人隔离、学习反馈和同步不在产品边界。 |
| 外部输入不决定业务 | 网页、客户端声明和供应商输出均需验证与最小化。 |

当前架构为第一阶段提案；真实提示质量、时延和来源可用性仍需后续证据验证。

## 1.6. 假设与验证

当前假设是：有限上下文、共享词库和规则足以产生低打扰提示；YouTube 字幕可用性、快速路径的超时降级和缓存收益仍须以真实样例验证。假设不构成个人状态或同步需求。
