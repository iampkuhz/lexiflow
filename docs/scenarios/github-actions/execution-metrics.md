# 1. 运行计时与发行统计

> 从[发行准备](first-release/preparation.md)进入。运行结果、验收资格和长期成功率是三个不同事实。

## 1.1. 单次调用计时

候选与晋升入口的 JSON 输出包含 `diagnostics`。`phases` 保存本次实际执行的 `phase` 与 `durationMs`；计时块失败也记录耗时，未运行阶段没有通过记录。`elapsedMs` 是调用总耗时。候选准备的 `overheadMs` 包含阶段外的扫描、拷贝、现场准备与交接等工作；不能仅以阶段列表相加代替总时间。晋升入口记录覆盖整个调用的单个阶段，不输出 `overheadMs`。`failurePhase` 指向失败层，`remoteWriteState` 区分尚未写入、确认未发布、已发布和未知状态。日志不保存凭据或私有环境值。

候选准备分别记录环境／输入预检、编译、npm 准备、扩展打包、资料验证、镜像构建、组装及候选完整性校验；晋升分别记录只读预检与发布。调用总时间还包含源码扫描、制品读取、交接与进程清理，不能只把阶段列表相加作为端到端时间。完整自动化验证的执行与清理时间取当次 verification report 和隔离 lease，不把它移出统计范围。

GitHub 日志保留调用输出；当次原始 Check 报告与发布事件保留在既有 ignored 证据目录。计时不是独立验证或人审证据，`awaiting-native-formal` 更不表示发行成功。不同 checkout 即便同一 commit 也分开记录。

## 1.2. 可比较样本

每个样本绑定实际仓库根、精确源码身份、候选与制品摘要、工具版本、平台、输入规模、完整必需 Check 集合、依赖缓存和构建输出状态。冷缓存应区分“依赖缓存为空”和“构建输出为空”；热缓存也不能仅凭有 cache 目录推断命中。没有可核验缓存条件的历史记录只作诊断，不计算相对收益。

自动化关键路径涵盖编译、打包、全部必需自动化验证、晋升预检、发布执行及其有界异常确认与清理。准备工作若是完成同一交付目标所必需，也计入；不能以换进程、换阶段或转为后台排除。并行工作报告实际关键路径及资源竞争，不累加成虚假墙钟收益。

排队、一次人审、原生 actor 调度和外部等待单列；端到端墙钟从就绪后首次正式启动到完整交付终态，包含这些等待。未授权的公开发布不执行，发布耗时与完整端到端收益随之记为未证明，而不是零。

## 1.3. 首轮统计口径

发行观察单位为同一源码／正式输入与发行身份的一次完整交付，不是单个 job 或最后一次重跑。以候选摘要、源码身份与原生送验记录串联 private prepare、独立验证／审查和 promotion 的运行 ID；变更源码或重建不能重置同一失败样本。

| 分类 | 可核验判据 | 正常首轮率分母 |
| --- | --- | --- |
| `first-success` | 正式输入与必需环境就绪后，首次完整链成功；无临时改码、补配置、重建或新恢复运行 | 计入，计成功 |
| `first-failure` | 正常就绪的首次链失败、阻断或留下无法确认的远端状态 | 计入，不计成功 |
| `recovered-success` | 首次链失败，后续修复／补配置／重建或另开恢复运行后成功 | 计入，不计首轮成功 |
| `not-ready` | 正式启动前的就绪预检明确证明输入、许可、身份或环境缺项，尚未进入正常链 | 单列，不计入 |
| `fault-injection` | 启动前已标记的主动故障验证，不是正常发行 | 单列，不计入 |

首轮率为 `first-success / (first-success + first-failure + recovered-success)`。恢复后成功不能把原失败从分母删除；不能事后把正常运行中的环境故障改标为 `not-ready`。已知的一次人工审批不算返工；原运行内既有安全有界的只读确认可以计入首轮成功，前提是最后取得精确确认，不把未知结果当成功。

持续观察记录使用 ignored 证据表，每行保留样本 ID、类别、就绪证据、首次启动与终态时间、全部原始运行 ID、源码／候选摘要、自动化各阶段与外部等待、异常是否在原运行内收敛，以及恢复关联。只有完整链终态可进入正常率；待完成样本单列，不用 prepare 或 precheck 的 PASS 填充分子。真实样本数量与观察区间同时报告，一次成功不能证明长期达到 95%。

## 1.4. 失败现场与安全后续

先依据固定 `reason`、`failurePhase`、命令日志及发布事件定位输入、环境、构建、候选、验收或远端传输层。环境／输入被前置拒绝时不启动昂贵构建；候选目录、原始请求、摘要、handoff 与失败日志保留供核对，不直接删除锁或替换旧证据来重跑。

`prebuild-setup` 表示工具预检已通过，但本地锁、配置、缓存链接或输出目录准备失败；此时没有远端发布。构建开始后或进程硬中断留下的版本目录是待核对现场，不自动清除未知锁，不将同版本再次启动视为无痕首次运行。候选构建仅链接已校验的依赖缓存、Wrapper 对应的 Gradle 生成缓存与转换 JAR 缓存，不继承 `init.d`、`gradle.properties`、daemon 或任务输出缓存。Docker 可执行文件与 CI 的 `PATH` 仍须来自可信运行器安装，不接受不可信工作区可执行文件。

发布期间 `published`／`unknown` 是远端事实边界，不等于本机进程成功。未知写入继续按现有发布器在原运行内有界只读核对同一 draft 和精确附件；无法确认则失败关闭。后续只读确认现场、核对已存在镜像／附件与授权范围，再决定恢复；不能盲目重传、覆盖同版本、重新构建或借用旧批准。
