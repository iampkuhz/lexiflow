# 步骤 6：判断第一阶段能否结束

G1 要同时具备可评审的设计、当前前置收据、用户决定和有效出口收据。它没有一个“构建成功就进入第二阶段”的捷径。这一步以看文件和核对证据为主。

## 1. 确认评审对象完整

依次看 [需求追踪](../../reviews/phase-1-user-requirement-traceability.md)、[架构阅读入口](../../architecture/README.md)、[十项 ADR](../../architecture/decisions.md)、[G1 决策包](../../reviews/g1-decision-package.md)。

应能从用户需求找到负责人、主链路、失败/一致性合同、取舍与待验证假设。ADR Proposed 不等于已接受，初始 SLO / 成本测量设计不等于实测达标。已有 Java 骨架也不证明后续业务已交付。

## 2. 核对当前前置链，而非历史计数

看 [目录](../../../planning/workstreams.yaml) 的 G1 退出任务与阻断闭包，再用 [任务证据映射](../../reviews/g1-task-evidence-map.md) 定位证据，按照 [步骤 5](05-receipts-and-acceptance.md) 重验当前输入绑定。

退出任务是 `LF-TSK-ARCH-0008`。前置集合由当前目录依赖闭包确定，不能数 PASS 字样判定通过；任务/变更、注册表、来源、策略与依赖收据必须匹配。

## 3. 前置齐全后提交用户决定

准备架构、ADR 替代方案 / 取舍、假设与实验方式、当前前置收据索引和公开 Gate 的实际结果，请用户明确接受、修改或拒绝。不要求依赖用户决定的出口任务先 PASS 才能请求决定。批准前若仅缺用户决定，其余技术前置也必须先证明完成，不能将该 BLOCKED 用作下一阶段前置 PASS。批准不是重跑全量交付测试的理由。

不得自行写 APPROVED 标记。用户要求继续优化第一阶段、文档提交或工程构建通过，都不是阶段 2 的批准。新决定必须保留可追溯来源并绑定对应输入版本。

## 4. 条件具备时检查出口任务

下面的直接命令只做出口文档合同诊断，不签发正式出口收据：

```bash
python3 -m scripts.gates.task_contracts --task-id LF-TSK-ARCH-0008
```

看 `status`、`assertions` 和 `missing_terms`。缺精确批准标记可能得到 `BLOCKED`；其他前置缺项仍要单独记录，不能把所有阻塞缩成“只差用户批准”。不要重复运行它等待批准，也不要手加标记制造 PASS。

有明确用户批准后，依照现有签发者 / Gate 合同签发当前出口收据；同时核对 G1 PASS 与 APPROVED 才有后续准入。批准改变决定记录时，更新受影响的新输入绑定，不篡改历史收据。

## 判断与下一步

出口条件全部满足之前，阶段退出记 `BLOCKED`；任何实际校验失败保留其 `FAIL`。当前结果只见[阶段状态](../../roadmap/phase-1-status.md)。

本页不执行数据模型、业务 API、提示词、Compose 或扩展的后续实现。批准后的独立干净环境复现看 [工具链复现计划](../post-approval-toolchain-verification.md)：其中含未来入口与模板，不是当前全部可运行的命令清单。

## 工具链阶段边界

`OPS-0001` 的阶段 1 交付物是技术选择 ADR、当前环境差异与批准后的精确复现计划。已有 Java 25/Gradle/Spring Boot工程底座来自用户后续明确要求的 Java harness 实施；存在的文件不能再描述为未创建。该底座不证明产品业务或双环境复现完成。

批准后的干净外部环境复现、扩展运行时/包管理器固定版本、部署编排与产品实现由后续阶段的 OPS/数据/API 任务承担。不能把这些批准后才执行的动作反向作为请求 G1 批准前的条件。已声明的阶段 1 架构、工具链选择、harness 与正式当前输入验收仍保留完整要求。
