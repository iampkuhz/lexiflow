# 校验指导手册

校验先回答“我要证明什么”，再选择命令与证据。**设计可评审、工程检查通过、正式任务验收通过、用户同意进入下一阶段，是四个不同的结论。** 本集合把它们分开，方便你逐步操作和定位问题。

当前范围是第一阶段架构 / Java 基础。先执行 [步骤 1：确认范围](01-scope-and-preparation.md)，再按下表选路线；不用每次把全部命令跑一遍。

## 按目的选择路线

| 这次想确认什么 | 操作路线 | 最终能得到的结论 |
|---|---|---|
| 架构是否易懂、完整、图文一致 | 1 → [2：架构与图解](02-architecture-and-diagrams.md) | 设计审查结论与缺项清单 |
| Java 改动是否满足全部工程要求 | 1 → [3A：聚合检查](03-java-engineering.md#route-a) | 直接工程检查结果 |
| 单独观察某个 Java 工具 / 模块 | 1 → [3B：单项控制台检查](03-java-engineering.md#route-b) | 所选检查的结果与原生诊断 |
| 运行器 / Gate / 调度配置是否可用 | 1 → [4：Harness 与调度](04-harness-and-dispatch.md) | 配置与相应工具测试结果 |
| 某个任务能否正式验收 | 1 → 对应交付路线 → [5：收据与验收](05-receipts-and-acceptance.md) | 当前输入验证 / 审查 / 目录收据 |
| 第一阶段能否结束 | 前置任务正式验收 → [6：G1 决定](06-phase1-decision.md) | 用户决定与 G1 出口状态 |

只读理解架构时，步骤 2 看文件即可。纯文档修改不需要 Java 完整构建；Java 规则没有变化时也不需要重新做隔离执法反例。失败后按 [故障定位](troubleshooting.md) 修复对应层，再运行受影响检查。

## 每一步怎样使用

各页依次说明 **前提 → 操作 → 查看产物 → 判断 → 下一步**。直接命令在仓库根运行；带 `<actual-...>` 的命令是条件模板，必须先换成真实路径或身份。不要直接执行占位符，也不要把作者本地 `tmp/` 脚本当作仓库公共入口。

用 [校验记录模板](record-template.md) 保存命令、退出码、输入版本和证据位置。模板是人工记录，不能签发正式收据。日志、证据包、学习数据等本地证据留在忽略的 `tmp/`。

Java 操作页旁的 [Gradle 命令/脚本/任务全表](java-gradle-task-reference.md) 提供完整执行映射，不必根据任务名猜测检查范围。

## 证明边界

本手册只描述方法，不维护历史测试次数和阶段状态。当前结论见[阶段状态](../../roadmap/phase-1-status.md)。Java 构建与质量检查成功不等于业务旅程完成，也不替代正式任务收据。

缺可信证据包或签发者时，公开增量 Gate 拒绝执行正式验收，保留实际 FAIL 原因。精确约束以 [AGENTS.md](../../../AGENTS.md)、[Harness](../../../harness/README.md)、当前目录及对应工具配置为准。
