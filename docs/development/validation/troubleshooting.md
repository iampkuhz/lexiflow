# 校验失败时怎么看

先找最早失败的层，再看该层的输入和产物。保留原始结果，修复后创建新证据；没有输入变化、没有新问题时，不反复重跑已通过的聚合。

## 入口与工程失败

| 看到的现象 | 先看什么 | 下一步 |
|---|---|---|
| `Java toolchain FAIL` / 退出 2 | 启动器错误、JDK home 的 `release`、Java 清单 | 准备正确 Temurin 25；再做版本检查，不切到 26 |
| `Task ... not found` | `backend/settings.gradle.kts`、根构建、共享约定插件 | 用真实项目 / 任务；未来计划中的入口缺失记未完成，不能当通过 |
| Spotless 失败 | 当前日志指出的源码 | 修正格式，或显式 spotlessApply 后审差异 |
| Checkstyle / PMD 失败 | 失败叶模块的 XML/HTML、共享配置 | 修复已启用规则的问题；不抑制 PMD 或复制 Python 规则 |
| Java 源码 gate 失败 | report.json 的 gate / 违规、对应源码行 | 回到注释、记录 Javadoc 或抑制的真实 Java 负责人 |
| 架构失败 | 架构测试 HTML/XML、项目依赖结果和模块边界 | 区分类依赖、项目依赖、编译输入缺失与产品范围为空 |
| 测试失败/跳过/报告缺失 | 当前测试 XML、verify-no-skipped-tests、日志 | 修复对应测试或产物缺失；不借旧 XML、过滤失败测试或称零测试为业务完成 |
| 覆盖率偏低 | JaCoCo 报告的实际分母与代码范围 | 作为诊断；当前没有最低阈值，不自行添加成功结论 |

报告路径与定向命令统一查 [Java 手册](03-java-engineering.md)，不要另跑一套源码扫描器。

## 治理与完成信号失败

| 原因 / 状态 | 先看什么 | 下一步 |
|---|---|---|
| `missing-evidence-context` | 证据 / 签发者定位是否由受信运行时提供 | 保留实际 CLI FAIL；取得真实上下文前正式验收 BLOCKED |
| `evidence-context-conflict` | CLI 定位与 LEXIFLOW_GATE_* 来源 | 统一真实绑定；不要用任意证据包替换 |
| `identity-drift` / 未授权签发者 | 当前运行时绑定、签发者权限来源、精确映射 | 修正受信上下文或授权；不能随机换会话 / 执行者 |
| `input-drift` / `hash-graph-invalid` | 细节的定位、原引用 SHA、当前负责人字节 | 确认真正影响范围，准备新版本证据；旧收据不重写 |
| `BLOCKED` / 必需术语缺失 | task_contracts 的断言 / required_inputs | 补设计缺项；这个词汇结果不等于正式收据 |
| Qoder `BUSY` / `unknown` | 固定运行的完成记录 / 生命周期，必要进程证据 | 确认旧运行终态；不补开第二个，不循环查询 |
| 回调 `queued` | 精确父会话路由与完成落盘产物 | 只表示通知排队；验收走规范产物与收据，不算 PASS |
| 已 ack / superseded 的旧回调 | ack / 生命周期与精确运行 id | 结束该回调，不重复业务验收 |
| 规范核验器 FAIL | 阻断发现、准确产物定位 | 修复缺产物、结构定义或版本绑定；不读子代理全部聊天上下文 |

正式验收操作统一查 [收据手册](05-receipts-and-acceptance.md)。状态读取不是完整 DAG 验证；哈希 DAG 诊断也不是授权或 G1 的全部验收。

## Qoder 诊断与显式恢复

### 诊断顺序

优先读取结构化 `Result`，区分 `result_error_code`、原始 `service_code`、`http_status` 和进程退出码；不能用 HTTP 403 或退出 1 推断具体认证/额度原因。诊断入口为 `scripts/harness/qoder_task.py`，规则以共享 Harness 为准。

- 完成记录仅保存固定失败分类、动作、错误码、可重试性和诊断来源；回调不带日志、提示词、凭据或计费链接。
- 缺少传输信息时，只补读一次有界、PID/会话/目录/开始时间匹配的 CLI 运行日志。身份不明确、时间不符或符号链接日志忽略，不读取私人会话正文。
- 静态预检的 `model_access_checked: false` 表明它不证明账号或模型可用；工具与上下文检查通过也不是产品验收。
- 禁止内部模型请求重试；活动/未知状态护栏和派发锁保留。按稳定任务 ID 计算一次初始、一次修正，改工作包、主任务或版本不能重置额度；缺任务集合的旧记录只计已知主任务。
- 已知账号拒绝即使 ACK 后也继续阻断派发。ACK 只证明结果已消费，不修复账号容量。

### 显式恢复

操作者先在[官方用量面板](https://docs.qoder.com/cli/usage)核对账号计划与额度并解决外部问题，不静默切换模型、供应商或账号。

外部阻断解除后，父代理才可显式使用 `resume --followup` 并提供 `--runtime-recovery-confirmed`；新且未尝试的工作包也可在 `start` 使用该确认。任务合同、范围、哈希绑定预检、单活跃限制和稳定任务次数限制仍须通过，不自动重启失败运行。

该参数只是操作者声明，不是余额或权限探测。运行器在本地 `runtime-recovery.json` 保存来源，`account_access_verified: false`，不扩展冻结交接字段。

离线样例只证明诊断与护栏逻辑，不证明账号余额、服务可用或正式验收。

## 需要记录哪一种结果

`PASS` 只覆盖明确且完整执行的范围；`FAIL` 保留实际检查拒绝及原因；`BLOCKED` 说明必要前提未满足。命令退出码、生命周期 finished、人工记录和正式收据是不同信息，不互相覆盖。

用 [记录模板](record-template.md) 把“命令返回 FAIL”与“下一层因缺前提 BLOCKED”分别记下。修复后的通过记录引用新输入，先前失败仍保留。
