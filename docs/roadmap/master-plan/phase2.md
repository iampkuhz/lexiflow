# 1. 第二阶段：提示处理主线与功能分层

本阶段先回答“词汇资料怎样形成提示”，再确定内部模块。核心主线为：**来源资料 → 离线预处理与发布 → 服务启动装载 → 当前字幕处理 → 提示展示**。架构图表达已确定的功能设计，不是改造的出发点。

## 1.1. 具体结果

1. 分开词段类型、通用基础／重点／长尾分类、资料质量、提示资格与缓存资格；低频和缺失频率不直接阻断，不推断个人熟练度。
2. 形成来源解析、词形处理、分类证据、短语质量、默认义准备和原子发布的完整预处理流程。
3. 明确启动检查、发布身份、正负预热与空资料／故障行为；不静默使用演示资料代替正式词库。
4. 明确一次请求的校验、增量区间、候选生成、版本化查询、匹配资格、冲突选择和返回展示顺序。
5. 明确日志模板、原因码、字段单位和打印时机；敏感分析资料与普通指标分开。
6. 按功能合同调整代码、接口和测试，再形成架构与时序图。
7. 保留 macOS 本机调试，增加 Docker 服务发布；统一版本、制品和使用流程，具体见[发布与使用闭环](phase2/release.md)。

## 1.2. 范围与边界

允许按明确规则和验收样例调整提示资格、过滤与优先级，不仅做行为不变的拆类。观看仍只读取已发布资料，采用默认首义，不引入模型、前缀上下文消歧、四词以上新识别算法或分析队列。英文不等后端；不新增数据采集授权，不操作用户运行库。

性能专项、完整多义项资产和知识补充从本阶段分离，统一进入[后续待办池](future.md)。候选生成中的词组前缀索引与选义中的前文语境是不同能力，不混称“前缀优化”。
