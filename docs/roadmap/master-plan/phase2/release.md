# 1. 发布与使用闭环

上级：[第二阶段](../phase2.md)。本页规定二期交付目标，不表示相关能力已经实现；执行与证据见[状态页](status.md)。

## 1.1. 两种运行形式

| 形式 | 使用者与入口 | 交付边界 |
| --- | --- | --- |
| macOS 本机调试 | 开发者编译后端与扩展，使用本机工程启动入口 | 只支持 macOS 的源码调试；保留 Java 25 工程工具链，不制作桌面安装包 |
| Docker 服务发布 | 使用者取得预构建镜像、Compose 配置及匹配扩展包 | 宿主只要求 Docker Engine/Compose 和 Chrome；无需 Java、Python、Node、Gradle 或手工安装数据库 |

两种形式运行同一套 API、资料合同和业务代码，不能维护两套提示算法。服务端仍是唯一 API Modular Monolith，PostgreSQL 是独立基础设施，不新建产品 worker。Redis 不因为存在开发配置就成为发布必需依赖；仅有实际产品消费者时纳入。

Docker 默认将 API 发布到宿主 127.0.0.1，与扩展现有本机权限一致；数据库不发布宿主端口。容器内监听与宿主端口发布分别配置。二期不默认扩展到公网托管、远程字幕上传、账号或偏好同步。

## 1.2. 发行产物与版本

- 单一软件版本真源驱动后端和扩展构建，禁止多处独立填写发布版本。
- 发布清单记录源码提交、软件版本、API 合同、SQL 摘要、资料身份、预处理规则、镜像 digest、扩展摘要及许可材料；软件版本不能代替资料身份。
- 交付 API 镜像、固定版本/摘要的数据库依赖、Compose 配置、可分发的已发布资料包、匹配扩展 ZIP、校验清单和最短使用指南。
- 普通使用者不再提供或解析来源 CSV；资料包必须核对来源与许可，可验证身份和完整性，初始化失败不得标为就绪。
- 镜像目标为 Linux amd64/arm64；各架构分别构建和启动验证，只有实际通过者可列为支持，不能用 macOS 本机测试代替容器测试。
- Chrome 扩展 ZIP 不等于商店已发布；二期说明实际安装步骤，不声称免开发者模式。商店上传、镜像推送及签名凭据使用须另行取得明确授权。

## 1.3. 用户流程与故障恢复

取得发行文件 → 校验匹配版本 → Compose 启动 → 自动准备隔离资料空间 → 就绪检查 → 安装匹配扩展 → 开启英文字幕。

用户可查看未启动、初始化中、资料不可用、协议不匹配和已就绪等明确状态。首次准备有步骤与失败原因，重试不能重复破坏已有数据。服务不可用时仍保留英文。

更新先验证并准备完整的新软件/资料组合，再切换；不对既有数据空间执行开发库重建。资料和缓存分别管理，缓存可重建，发布身份不得复用绑定不同内容。失败保留原安装及可恢复入口，不假设跨版本结构兼容。扩展本机抑制偏好不因后端更新而清除。

停止服务不删除数据卷；卸载明确区分程序、词库、敏感记录与浏览器偏好的保留和删除。默认诊断不含字幕、释义、观看 URL 或凭据；正式包不继承开发者个人的敏感分析记录授权。

## 1.4. 实施工作与交付目标

| 顺序 | 具体工作 | 验收目标 |
| --- | --- | --- |
| 1 | 统一版本读取、发布清单生成和消费端匹配校验 | 修改一处版本即可生成匹配产物；错误组合拒绝启动提示链 |
| 2 | 已发布资料打包、完整性校验和首次初始化入口 | 用户无需导入 CSV；重复启动幂等，错误资料不可用但不破坏旧资料 |
| 3 | API Dockerfile、运行配置、Compose 和健康检查 | 无开发环境的宿主可启动；数据库私网，API 默认仅本机可达 |
| 4 | 固定依赖的自动构建、双架构验证、扩展打包和许可清单 | 制品可追溯，任一必需检查失败不得正式发布，不自动上传 |
| 5 | 启动状态、最短使用指南、更新/恢复/卸载流程 | 用户能自行识别服务与资料状态，故障有明确恢复动作 |
| 6 | 干净环境安装、重启、更新失败和真实视频验收 | 验证完整使用闭环，不用开发机启动或合成页面代替 |

发布任务在总验收前完成，并以可独立构建验证的工作片纳入 Catalog；不能只交付 Dockerfile 或 ZIP 就宣称开箱即用。

## 1.5. 资源验收

二期采用以下工程验收上限，不是已达到的实测成绩，也不是建议用户采购的硬件配置。基准运行环境为 4 个逻辑 CPU、8 GiB 内存、SSD，给 Docker 中的 API 与 PostgreSQL 合计不超过 2 GiB 内存；宿主运行 Chrome 观看一条英文视频，不要求 GPU 或模型。记录 OS、Docker 版本、CPU 架构和资源限制，amd64/arm64 分别用原生运行环境测量；模拟架构的构建成功不能证明原生性能。

| 项目 | 上限与测量条件 |
| --- | --- |
| 首次发行下载 | API 镜像、数据库镜像、压缩资料及扩展合计不超过 3 GiB，按制品字节计，不把带宽换算成固定下载时间 |
| 日常安装磁盘 | 全部运行镜像、展开资料和一个活动数据空间合计不超过 8 GiB；保留一次更新恢复空间时合计不超过 16 GiB |
| 首次资料初始化 | 制品已在本机、空的隔离资料空间，开始初始化至正式就绪不超过 10 分钟；不计网络下载 |
| 日常冷启动 | 已初始化资料、进程全部停止后启动至正式就绪不超过 30 秒；不是空库初始化 |
| 服务内存 | API 和 PostgreSQL 总 cgroup 内存峰值不超过 2 GiB，包括文件缓存；不只报告 JVM heap |
| 空闲 CPU | 就绪后静置 60 秒，再测 120 秒，总 CPU 平均不超过 0.05 个逻辑核 |
| 播放 CPU | 单客户端连续至少 375 秒合成字幕（每秒一次变化），总 CPU 平均不超过 1 个逻辑核，同时记录峰值 |
| 稳态提示处理 | 同一播放样本预热 30 秒后，后端端到端耗时 p95 不超过 150 ms；错误/超时计入失败，不从统计中静默剔除 |

分别记录冷/热状态、样本数、失败数和分母。真实视频体验另行验证，不用上述合成样本宣称普遍语义正确率。实测超限应先分析并修复，不得由实施者直接放宽预算；必需平台或预算缺证据为 BLOCKED。Docker 本身仍是使用者需安装的运行环境，不宣称零环境依赖。

## 1.6. Catalog 任务与依赖

以下任务均须连同直接测试交付。文件范围、检查及精确依赖版本以 [Catalog](../../../../planning/workstreams.yaml) 为准；此处列出可读的责任与交接。验证命令属于对应实现交付物，入口尚不存在时不得跳过或冒充已运行。

### 1.6.1. LF-TSK-ARCH-2006 · 冻结双运行形式、发布身份和使用闭环合同

- 主责：`LF-WS-ARCH`；预计 60 分钟；前置：`LF-TSK-ARCH-2003`。
- 确定 macOS 调试与 Docker 发布共用业务链、容器端口/资料/隐私边界；不制作桌面安装包，不自动开放公网。
- 冻结版本真源、镜像/资料/扩展清单、首次初始化、更新恢复及卸载的输入输出和失败动作。
- 明确 linux amd64/arm64 验证、资源预算及必需发布凭据；没有实测/外部许可不得标为支持或正式发布。

### 1.6.2. LF-TSK-OPS-2003 · 建立软件版本真源并接入后端构建

- 主责：`LF-WS-OPS`；预计 60 分钟；前置：`LF-TSK-ARCH-2006`。
- 软件版本由 ops/release/version.txt 唯一维护，三段数字格式有界校验；后端构建和清单读取同一来源。
- 异常格式、缺失版本、发行构建的脏源码输入必须可检测；不自动修改 Git tag 或推送。

### 1.6.3. LF-TSK-EXT-2003 · 让扩展构建消费统一版本并产出匹配扩展包

- 主责：`LF-WS-EXT`；预计 60 分钟；前置：`LF-TSK-OPS-2003`。
- 移除独立发布版本填写点，生成 manifest 与 ZIP 时从同一软件版本真源读取；保留本机 API 权限。
- ZIP 仅含运行所需 dist 文件；排除源码、测试、私有配置，构建格式及清单摘要有直接测试。

### 1.6.4. LF-TSK-OPS-2004 · 实现发布清单、摘要和许可材料打包

- 主责：`LF-WS-OPS`；预计 75 分钟；前置：`LF-TSK-OPS-2003`、`LF-TSK-EXT-2003`。
- 清单绑定源码、软件/API/SQL/资料/准备策略、架构和全部制品摘要；拒绝缺项、路径逃逸和被篡改内容。
- 许可和来源依据随制品交付，缺少必需资料不得发行；构建机私有路径和凭据不进入清单。

### 1.6.5. LF-TSK-OPS-2005 · 构建已发布词库资料包与隔离初始化

- 主责：`LF-WS-OPS`；预计 90 分钟；前置：`LF-TSK-OPS-2001`、`LF-TSK-OPS-2004`。
- 仅导出经批准且有来源/许可的已发布资料，不打包开发者日志、观看记录和配置；身份、SQL 摘要与清单一致。
- 使用者无需原始 CSV，资料包通过完整性校验后仅初始化明确归属的空数据空间；已有不同资料不覆盖。
- 在隔离 PostgreSQL 验证重复启动、损坏包、初始化中断及无资料行为，未发布状态不能就绪。

### 1.6.6. LF-TSK-API-2003 · 提供发布就绪合同并隔离发行包敏感记录授权

- 主责：`LF-WS-API`；预计 75 分钟；前置：`LF-TSK-API-2001`、`LF-TSK-ARCH-2006`。
- 就绪响应含软件/API/资料身份及固定原因，无发布资料、结构错误或依赖故障不得显示就绪；不泄漏连接凭据。
- 发行启动默认不记录敏感字幕；保留用户明确授权的 macOS 调试记录边界，普通日志仍无正文。

### 1.6.7. LF-TSK-EXT-2004 · 展示服务与资料状态并拒绝不匹配协议

- 主责：`LF-WS-EXT`；预计 75 分钟；前置：`LF-TSK-API-2003`、`LF-TSK-EXT-2002`、`LF-TSK-EXT-2003`。
- 弹窗明确区分未启动、初始化中、资料不可用、协议不匹配与就绪，并提供对应操作指引。
- 不匹配协议不发送字幕；状态探测不阻塞英文、不扩大主机权限，不读取或上传本机抑制偏好。

### 1.6.8. LF-TSK-OPS-2006 · 封装 API 镜像和私网数据库 Compose

- 主责：`LF-WS-OPS`；预计 90 分钟；前置：`LF-TSK-OPS-2005`、`LF-TSK-API-2003`。
- 使用预构建产品与运行时镜像，不在最终镜像包含 Java 编译器、Python/Node 工程环境、源 CSV 或本机配置。
- API 宿主默认只绑定 127.0.0.1，PostgreSQL 不发布宿主端口；产品无实际依赖时不启 Redis。
- 以非 root API、独立持久卷和明确健康依赖启动；隔离测试覆盖端口冲突、缺资料、重启和停止。

### 1.6.9. LF-TSK-OPS-2007 · 实现匹配制品更新与失败恢复操作

- 主责：`LF-WS-OPS`；预计 90 分钟；前置：`LF-TSK-OPS-2006`。
- 新制品先校验并准备独立数据空间，准备失败仍能使用原安装；不在原库执行开发重建。
- 恢复绑定匹配软件/结构/资料组合，不仅替换可执行文件；停止与删除分开，删除数据须明确确认。
- 隔离演练中断、空间不足和错误版本；扩展偏好不因后端生命周期被删除，不操作真实运行卷。

### 1.6.10. LF-TSK-OPS-2008 · 串联双架构构建与受控发布流水线

- 主责：`LF-WS-OPS`；预计 90 分钟；前置：`LF-TSK-OPS-2004`、`LF-TSK-OPS-2006`、`LF-TSK-OPS-2007`、`LF-TSK-EXT-2004`。
- 固定依赖并生成 linux amd64/arm64 镜像及匹配资料/扩展清单；两个架构分别启动验证，不用仅构建通过代替。
- 测试失败、许可缺失、未验证架构均不得进入正式发行清单；本地默认只产物构建，不上传。
- 公开上传、商店提交和凭据使用保留人工授权，CI 不自动合并或签发 Formal Gate。

### 1.6.11. LF-TSK-ARCH-2007 · 编写双运行入口和用户安装更新指南

- 主责：`LF-WS-ARCH`；预计 60 分钟；前置：`LF-TSK-OPS-2008`。

### 1.6.12. LF-TSK-QLT-2002 · 验证干净环境发布闭环和资源门槛

- 主责：`LF-WS-QLT`；预计 90 分钟；前置：`LF-TSK-OPS-2008`、`LF-TSK-ARCH-2007`、`LF-TSK-QLT-2001`。

- 真实用户视频与合成测试分开；冻结相同输入供独立 validation/review，未完成 Formal Gate 不称正式交付。
