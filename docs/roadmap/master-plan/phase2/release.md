# 1. 发布与使用闭环

上级：[第二阶段](../phase2.md)。本页规定二期交付目标，不表示相关能力已经实现；执行与证据见[状态页](status.md)。

## 1.1. 两种运行形式

| 形式 | 使用者与入口 | 交付边界 |
| --- | --- | --- |
| macOS 本机调试 | 开发者编译后端与扩展，使用本机工程启动入口 | 只支持 macOS 的源码调试；保留 Java 25 工程工具链，不制作桌面安装包 |
| Docker 服务发布 | 使用者取得预构建镜像、Compose 配置及匹配扩展包 | 宿主只要求 Docker Engine/Compose 和 Chrome；无需 Java、Python、Node、Gradle 或手工安装数据库 |

两种形式运行同一套 API、资料合同和业务代码，不能维护两套提示算法。服务端仍是唯一 API Modular Monolith，PostgreSQL 是独立基础设施，不新建产品 worker。Redis 不因为存在开发配置就成为发布必需依赖；仅有实际产品消费者时纳入。

Docker 默认将 API 发布到宿主 127.0.0.1，与扩展现有本机权限一致；数据库不发布宿主端口。容器内监听与宿主端口发布分别配置。二期不默认扩展到公网托管、远程字幕上传、账号或偏好同步。

## 1.2. 发行产物与版本

- 单一软件版本真源驱动后端和扩展构建，禁止多处独立填写发布版本。
- 发布清单记录源码提交、软件版本、API 合同、SQL 摘要、资料身份、预处理规则、镜像 digest、扩展摘要及许可材料；软件版本不能代替资料身份。
- 交付 API 镜像、固定版本/摘要的数据库依赖、Compose 配置、可分发的已发布资料包、匹配扩展 ZIP、校验清单和最短使用指南。
- 普通使用者不再提供或解析来源 CSV；资料包必须核对来源与许可，可验证身份和完整性，初始化失败不得标为就绪。
- 当期仅支持 M 芯片 macOS 上的 Docker，镜像目标为 `linux/arm64`；必须在该宿主原生构建和启动验证，不能用源码本机测试代替容器测试。其他宿主与 `linux/amd64` 列入后续待办，不作为当期验收前置。
- Chrome 扩展 ZIP 不等于商店已发布；二期说明实际安装步骤，不声称免开发者模式。商店上传、镜像推送及签名凭据使用须另行取得明确授权。

## 1.3. 用户流程与故障恢复

取得发行文件 → 校验匹配版本 → Compose 启动 → 自动准备隔离资料空间 → 就绪检查 → 安装匹配扩展 → 开启英文字幕。

用户可查看未启动、初始化中、资料不可用、协议不匹配和已就绪等明确状态。首次准备有步骤与失败原因，重试不能重复破坏已有数据。服务不可用时仍保留英文。

更新先验证并准备完整的新软件/资料组合，再切换；不对既有数据空间执行开发库重建。资料和缓存分别管理，缓存可重建，发布身份不得复用绑定不同内容。失败保留原安装及可恢复入口，不假设跨版本结构兼容。扩展本机抑制偏好不因后端更新而清除。

停止服务不删除数据卷；卸载明确区分程序、词库、敏感记录与浏览器偏好的保留和删除。默认诊断不含字幕、释义、观看 URL 或凭据；正式包不继承开发者个人的敏感分析记录授权。

## 1.4. 实施工作与交付目标

| 顺序 | 具体工作 | 验收目标 |
| --- | --- | --- |
| 1 | 统一版本读取、发布清单生成和消费端匹配校验 | 修改一处版本即可生成匹配产物；错误组合拒绝启动提示链 |
| 2 | 已发布资料打包、完整性校验和首次初始化入口 | 用户无需导入 CSV；重复启动幂等，错误资料不可用但不破坏旧资料 |
| 3 | API Dockerfile、运行配置、Compose 和健康检查 | 无开发环境的宿主可启动；数据库私网，API 默认仅本机可达 |
| 4 | 固定依赖的自动构建、Apple Silicon 容器验证、扩展打包和许可清单 | 制品可追溯，任一必需检查失败不得正式发布，不自动上传 |
| 5 | 启动状态、最短使用指南、更新/恢复/卸载流程 | 用户能自行识别服务与资料状态，故障有明确恢复动作 |
| 6 | 干净环境安装、重启、更新失败和真实视频验收 | 验证完整使用闭环，不用开发机启动或合成页面代替 |

发布任务在总验收前完成，并以可独立构建验证的工作片纳入 Catalog；不能只交付 Dockerfile 或 ZIP 就宣称开箱即用。

## 1.5. 资源验收

二期采用以下工程验收上限，不是已达到的实测成绩，也不是建议用户采购的硬件配置。基准运行环境为 4 个逻辑 CPU、8 GiB 内存、SSD，给 Docker 中的 API 与 PostgreSQL 合计不超过 2 GiB 内存；宿主运行 Chrome 观看一条英文视频，不要求 GPU 或模型。记录 OS、Docker 版本、CPU 架构和资源限制，在 Apple Silicon macOS Docker 的原生 `linux/arm64` 环境测量；模拟架构的构建成功不能证明原生性能。

| 项目 | 上限与测量条件 |
| --- | --- |
| 首次发行下载 | API 镜像、数据库镜像、压缩资料及扩展合计不超过 3 GiB，按制品字节计，不把带宽换算成固定下载时间 |
| 日常安装磁盘 | 全部运行镜像、展开资料和一个活动数据空间合计不超过 8 GiB；保留一次更新恢复空间时合计不超过 16 GiB |
| 首次资料初始化 | 制品已在本机、空的隔离资料空间，开始初始化至正式就绪不超过 10 分钟；不计网络下载 |
| 日常冷启动 | 已初始化资料、进程全部停止后启动至正式就绪不超过 30 秒；不是空库初始化 |
| 服务内存 | API 和 PostgreSQL 总 cgroup 内存峰值不超过 2 GiB，包括文件缓存；不只报告 JVM heap |
| 空闲 CPU | 就绪后静置 60 秒，再测 120 秒，总 CPU 平均不超过 0.05 个逻辑核 |
| 播放 CPU | 单客户端连续至少 375 秒合成字幕（每秒一次变化），总 CPU 平均不超过 1 个逻辑核，同时记录峰值 |
| 稳态提示处理 | 同一播放样本预热 30 秒后，后端端到端耗时 p95 不超过 150 ms；错误/超时计入失败，不从统计中静默剔除 |

分别记录冷/热状态、样本数、失败数和分母。真实视频体验另行验证，不用上述合成样本宣称普遍语义正确率。实测超限应先分析并修复，不得由实施者直接放宽预算；必需平台或预算缺证据为 BLOCKED。Docker 本身仍是使用者需安装的运行环境，不宣称零环境依赖。

## 1.6. Catalog 任务与依赖

以下任务均须连同直接测试交付。文件范围、检查及精确依赖版本以 [Catalog](../../../../planning/workstreams.yaml) 为准；此处列出可读的责任与交接。验证命令属于对应实现交付物，入口尚不存在时不得跳过或冒充已运行。

### 1.6.1. LF-TSK-ARCH-2006 · 冻结双运行形式、发布身份和使用闭环合同

- 主责：`LF-WS-ARCH`；预计 60 分钟；前置：`LF-TSK-ARCH-2003`。
- 确定 macOS 调试与 Docker 发布共用业务链、容器端口/资料/隐私边界；不制作桌面安装包，不自动开放公网。
- 冻结版本真源、镜像/资料/扩展清单、首次初始化、更新恢复及卸载的输入输出和失败动作。
- 明确 Apple Silicon macOS Docker 的 linux/arm64 验证、资源预算及必需发布凭据；没有实测/外部许可不得标为支持或正式发布。

### 1.6.2. LF-TSK-OPS-2003 · 建立软件版本真源并接入后端构建

- 主责：`LF-WS-OPS`；预计 60 分钟；前置：`LF-TSK-ARCH-2006`。
- 软件版本由 ops/release/version.txt 唯一维护，三段数字格式有界校验；后端构建和清单读取同一来源。
- 异常格式、缺失版本、发行构建的脏源码输入必须可检测；不自动修改 Git tag 或推送。

#### 1.6.2.1. 版本与发行输入合同

`ops/release/version.txt` 是唯一软件版本真源，初始为 `0.1.0`；允许文件末尾一个 LF 或 CRLF，不接受其他空白、BOM、多行、后缀或前导零。格式固定 `major.minor.patch`，各段为 0～65535 且不能全零，遵循 [Chrome 版本字段约束](https://developer.chrome.com/docs/extensions/reference/manifest/version) 的三段子集。软件版本不改变 API/SQL/词库的独立身份。

Node 发布工具通过 `version.mjs` 读取、校验版本；Gradle 通过同合同的 build-logic parser 读取该文件，所有产品子项目及 JAR manifest 消费这个值，不接受第二个版本参数覆盖。两个 parser 都有边界测试；构建消费者按 Gradle 的实际归档输出定位，不扫描目录选中旧版本 JAR。

源码调试允许工作区改动；显式 `-Prelease=true` 的 Gradle 构建和 `node ops/release/version.mjs --release` 必须核对真实 Git 根、有效 HEAD，以及包括未跟踪文件的工作区/暂存区清洁状态。Git 不可用、空仓库或脏输入都拒绝，忽略的本机运行产物不当成发行源码；错误仅给固定原因，不打印私有文件名。检查不创建 tag、不提交、不上传。此处只证明发行输入资格，不代替后续许可、制品清单或 Docker 验收。

版本模块的 `check.mjs` 运行真实 Node 单测，并拒绝零测试、缺失结果、跳过、取消和失败；不以退出零直接判断通过。OPS-2003 的最小接线包括独立 release-version Check 的双 scope 声明、版本文件到后端的触发与冻结输入，以及声明回归测试；父代理集成 Harness 部分，不把 Node 测试塞进产品 Java 模块。QLT-2004 继续负责后续完整 Docker/发布验收入口，不等待它才验证版本基础。

### 1.6.3. LF-TSK-EXT-2003 · 让扩展构建消费统一版本并产出匹配扩展包

- 主责：`LF-WS-EXT`；预计 60 分钟；前置：`LF-TSK-OPS-2003`。
- 移除独立发布版本填写点，生成 manifest 与 ZIP 时从同一软件版本真源读取；保留本机 API 权限。
- ZIP 仅含运行所需 dist 文件；排除源码、测试、私有配置，构建格式及清单摘要有直接测试。

#### 1.6.3.1. 扩展构建与 ZIP 合同

`extension/manifest.json` 仅是无版本模板，私有 npm 工程及根 lock 元数据不再单独维护产品版本。普通构建和打包均调用统一 `ops/release/version.mjs`，生成 manifest 的 version；构建脚本不再允许版本覆盖参数。调试仍可显式选择本机端口，发行包固定 `http://127.0.0.1:18080/*`，不能把测试端口或远程地址带给使用者。

`npm --prefix extension run package` 在核对干净 Git 输入后重新构建，不能打包此前残留的 dist；完成后再次核对版本及源码身份。ZIP 使用锁定的构建期 ZIP 库，按固定顺序、固定 ZIP 时间与压缩参数生成，相同输入的字节及 SHA-256 一致；不手写归档格式，也不要求使用者安装打包工具。

打包允许集为 `manifest.json`、`background.js`、`content.js`、`youtube-bridge.js`、`popup.js`、`popup.html`、`popup.css`、四个尺寸的 PNG 图标及 `assets/logo.svg`。仅读取这些受控相对路径，拒绝必需文件缺失、被选文件或父目录符号链接、错误 manifest 版本/本机权限；额外源码、测试、map、配置和私有文件不进入 ZIP。所有候选文件先校验和读取，再写产物，不复制整个 dist。

输出位于 ignored `tmp/releases/<软件版本>/<源码提交>/`，包含 `lexiflow-extension-<版本>.zip` 和对应 `.sha256`，标准输出给出软件版本、源码提交、文件名、字节数与摘要供后续发布清单消费。重复运行相同内容可复用；同一路径已有不同内容则拒绝，不删除或覆盖旧制品。输出不等于上传商店或公开发布。

自动消费描述符使用 `npm --silent --prefix extension run package`，避免 npm 自身的启动横幅；也可从仓库根直接执行 `node extension/scripts/release.mjs`。两者使用同一正式入口，不支持绕过干净源码检查或覆盖版本。

直接测试覆盖版本生成、manifest/权限、ZIP 准确文件集合与字节、确定性、摘要、缺文件和符号链接，以及拒绝错误或脏发行输入。既有合成浏览器回归从同一打包函数产生的 ZIP 解包加载扩展；仅在临时测试副本调整到隔离 API，不更改发行包权限，不把合成页面结果称为真实 YouTube 验收。

### 1.6.4. LF-TSK-OPS-2004 · 实现发布清单、摘要和许可材料打包

- 主责：`LF-WS-OPS`；预计 75 分钟；前置：`LF-TSK-OPS-2003`、`LF-TSK-EXT-2003`。
- 清单绑定源码、软件/API/SQL/资料/准备策略、架构和全部制品摘要；拒绝缺项、路径逃逸和被篡改内容。
- 许可和来源依据随制品交付，缺少必需资料不得发行；构建机私有路径和凭据不进入清单。

#### 1.6.4.1. 清单、许可与目录装配合同

构建机清单工具只消费显式预构建制品，不访问运行数据库、用户来源 CSV 或本机日志。软件版本和源码提交由统一版本入口核对干净 Git 后取得。使用者取得已装配目录，不以 Node 构建工具作为启动依赖。

清单绑定 API 合同、SQL 身份和摘要、资料发布身份、预处理规则身份，以及每项制品的受控相对路径、大小和 SHA-256。镜像另有平台及 image digest（离线导入后的不可变 image ID，不与 registry manifest digest 混用）；平台集仅接受 `linux/amd64`、`linux/arm64`，每平台须有匹配 API 与 PostgreSQL 镜像。Compose、SQL、资料包、扩展、发行入口和许可文本均为必需制品；预期身份及摘要须与实际文件一致，不能重新计算摘要掩盖漂移。

每个制品引用随包许可记录，绑定组件、许可名称、公开来源依据与 notice 文件。LexiFlow、扩展第三方、API 运行时、PostgreSQL 和资料来源均不得缺项。工具校验完整性，不替代责任人核实许可真实性。

输入为严格结构，未知字段、非法类型、缺件、摘要篡改、路径逃逸及符号链接均拒绝。错误使用固定原因，不输出私有路径或凭据。输出按稳定顺序序列化，不带时间戳或构建机路径。

目录装配先完整验证，在临时兄弟目录复制并再次校验后原子发布。同内容才可复用，异常只清理本次临时目录。清单生成不代表镜像已启动或资料已获授权。

构建机从仓库根调用以下固定参数入口：

```sh
node ops/release/package.mjs \
  --source-repo /absolute/clean-source \
  --descriptor-file /absolute/release-input.json \
  --artifact-root /absolute/prebuilt-artifacts \
  --output-directory /absolute/output/release
```

描述符顶层字段为 `schemaVersion`、`softwareVersion`、`sourceCommit`、`apiContract`、`sqlVersion`、`dataset`、`platforms`、`artifacts`、`licenses`；严格字段和合成样例见 `ops/release/manifest.mjs` 与 `ops/release/tests/manifest.test.mjs`。装配过程不修改源码、描述符或制品。

`eng.release.manifest` 运行真实清单测试，冻结清单、装配入口、直接测试、版本读取器和许可说明；零测试、跳过、失败或输出不完整都不能 PASS。

### 1.6.5. 已发布资料快照与隔离初始化

- 主责：`LF-WS-OPS`；导出与初始化各预计 90 分钟；导出前置：`LF-TSK-OPS-2001`、`LF-TSK-OPS-2004`。
- 仅导出经批准且有来源/许可的已发布资料，不打包开发者日志、观看记录和配置；身份、SQL 摘要与清单一致。
- 使用者无需原始 CSV，资料包通过完整性校验后仅初始化明确归属的空数据空间；已有不同资料不覆盖。
- 在隔离 PostgreSQL 验证重复启动、损坏包、初始化中断及无资料行为，未发布状态不能就绪。

实现分为两项顺序任务：`LF-TSK-OPS-2009` 负责导出与离线校验，`LF-TSK-OPS-2005` 负责安全初始化和同一 API JAR 的管理入口；主责均为 `LF-WS-OPS`，每项预计 90 分钟。完整发行目标不变，初始化硬依赖经过验证的快照合同。

#### 1.6.5.1. Java 快照包与安全初始化

资料工具由 API 组合根提供一次性 `--release-dataset export|verify|initialize` 管理模式，完成后退出。数据搬运位于 Lexicon Java 持久化适配器，只恢复已发布事实和投影，不重跑来源 CSV 清洗。正式使用者在产品容器内执行同一 API JAR。

资料 ZIP 限于 manifest、来源审批记录及 dataset/prepared/lookup 三份 NDJSON；目录、未知条目、重复字段、摘要或条数不符均拒绝。导出在只读一致性快照中完成，保留发布版本、来源许可身份、准备策略及全量三表字段。

初始化只使用软件内嵌且摘要匹配的最新 SQL，不执行包内 SQL。目标数据库、schema 和 owner 须与显式输入一致，拒绝默认 public 或已有不同内容；受控初始化锁内一次事务完成结构、条目、投影和发布单行，失败回滚。只有内容摘要、版本、策略与条数完全相同才可复用。禁止调用开发重建工具。

导出与解压使用本次独占目录，拒绝符号链接和未知条目。处理流式且限制文件、单行与解压总量，格式上限不代替资源实测。最终 ZIP 摘要与准备策略交给发布清单，完整 PG 事务和故障行为由 Harness 隔离数据库的真实合成往返证明。

#### 1.6.5.2. ECDICT 精简来源输入

离线来源生成器使用锁定提交与文件摘要的 ECDICT 基础版 `ecdict.csv`，不把全量词库随机或按字母序截成固定数量。目标是保守精简约三分之一，而非硬配额；有 `bnc/frq` 正排名、Oxford、Collins 或考试标记的候选受保护。无上述标记时，仅按纯专名、纯冷门机构缩写、已验证原型词形覆盖的重复记录，以及全部释义明确属于选定冷僻领域的记录作有据剔除；混合普通义项或不能判断的保留。连字符、网络来源、长度或缺音标本身不构成删除理由。

基础词集合与词形覆盖不能因精简丢失；既有受审查中文映射使用锁定完整源中的精确原记录，逐条记录来源文件与原始行号，不把补充来源伪装成基础版原文。每次生成提供保留/剔除计数与可追溯原因，完整明细留在本次 ignored 输出目录，不包含用户观看数据。

构建输入 ZIP 使用固定 7 列 word、translation、oxford、tag、bnc、frq、exchange，保留中文原始释义、频率、词形和基础词证据；来源映射单列 source_row，以数据行顺序还原输出行号，纯数字指向 ecdict.csv、s: 前缀指向 stardict.csv，清单声明编码并保留严格解码能力。附 MIT 许可及摘要清单；不携带未使用的英文长释义、音标、音频等字段。目标压缩不超过 8 MiB、展开 CSV 不超过 32 MiB，超限须报告而非暗中削词。本阶段词库 ZIP、CSV 与其他压缩/展开数据均不进入 Git，只保留生成器、测试与小型来源锁；最终封版时经用户确认再纳入制品。原始下载和中间报告保持忽略。该来源 ZIP 不等于上一节 Java 已发布快照包；必须经过既有 Java 准备/发布/导出链，用户安装不解析来源 CSV，也不需要 Python。

#### 1.6.6.1. 状态查询与敏感记录开关

#### 1.6.7.1. 协议预检与状态展示

- 主责：`LF-WS-OPS`；预计 90 分钟；前置：`LF-TSK-OPS-2005`、`LF-TSK-API-2003`。

- API 宿主默认只绑定 127.0.0.1，PostgreSQL 不发布宿主端口；产品无实际依赖时不启 Redis。
- 以非 root API、独立持久卷和明确健康依赖启动；隔离测试覆盖端口冲突、缺资料、重启和停止。

#### 1.6.8.1. 容器运行边界

Compose 只装配 PostgreSQL、一次性资料初始化和 API，所有镜像均预构建且禁止自动拉取；初始化使用同一 API 镜像，不是产品 worker。项目作用域的数据卷和内部网络不共享真实安装；PG 无宿主端口，API 固定绑定宿主 `127.0.0.1:18080`。API 使用非 root、只读根文件系统、受限临时空间和固定 JVM 内存；这些配置不代替资源实测。

资料初始化等待 PG 最终 TCP 服务健康，API 等待初始化成功；失败不启动提示服务，不清除卷。初始化的大文件暂存在独立项目工作卷中，由 Java 清理本次临时文件；不使用 API 的小型内存临时空间承载整个资料包。应用使用独立于管理员的数据库角色与 secret，空卷基础设施 bootstrap 只创建该角色与受控 schema，词库三表仍由已校验的 Java 初始化事务负责。秘密来自安装目录，不包含在制品或默认配置中。 宿主密码文件保持私有权限，固定入口只在独立 Compose 子 shell 中读取并校验，然后通过 environment 来源的 secret 授权服务读取 `/run/secrets`；值不进入命令参数或服务 environment 配置。不能用宿主 0600 文件直接绑定并假定容器跨 UID 可读；实际容器权限仍需 Linux 运行验收。

健康检查由同一 JAR 的短命命令消费本机 readiness，不要求镜像内存在编译器、Python、Node 或 curl。Docker 上下文只开放指定 JAR、两份 Dockerfile 与两个运行脚本，不复制开发配置、源码或资料。PostgreSQL 镜像基于已固定的官方镜像，仅内置 bootstrap；不依赖发布清单之外的宿主脚本，脚本随镜像摘要一起验证。开发机的封装测试和真实容器运行验收分别记录；`eng.release.docker-contract` 在两种 Verify 范围执行真实封装单测并冻结 Docker 与健康探针输入，零测试或跳过失败关闭。该 Check 不签发真实容器验收；缺少受控运行环境不得用静态配置检查替代启动、重启和端口冲突验证。

### 1.6.9. LF-TSK-OPS-2007 · 实现匹配制品更新与失败恢复操作

- 主责：`LF-WS-OPS`；预计 90 分钟；前置：`LF-TSK-OPS-2011`。
- 新制品先校验并准备独立数据空间，准备失败仍能使用原安装；不在原库执行开发重建。
- 恢复绑定匹配软件/结构/资料组合，不仅替换可执行文件；停止与删除分开，删除数据须明确确认。
- 隔离演练中断、空间不足和错误版本；扩展偏好不因后端生命周期被删除，不操作真实运行卷。

#### 1.6.9.1. 发行入口与离线匹配校验

`LF-TSK-OPS-2010` 单独负责发行入口生成与离线校验，主责 OPS、预计 90 分钟、前置 OPS-2004；OPS-2011 负责私有安装状态、锁与受控 Docker 资源准备，OPS-2007 负责随后有状态的更新恢复操作。拆分是制品校验、资源归属与运行状态机的职责划分，不减少更新失败保留原安装的要求。

构建端 `runtime-entry.mjs` 生成受完整清单绑定的 `lexiflow.sh`，以 `runtime-entry` 制品角色交付并引用 LexiFlow 许可；使用者明确通过 `sh` 调用，不依赖执行位或宿主 Node、Java、Python。系统 shell 与文件/摘要工具是 macOS/Linux 用户入口的操作前提，不据此宣称支持 Windows 原生入口。

入口固化全部制品的路径、大小与摘要，以及完整软件、API、SQL、资料、准备规则和镜像组合身份。每次进入生命周期操作，先验证发行文件；规范清单除入口自身的大小和摘要槽外全部固化，验证时仅用实际入口文件填入这两个槽，避免摘要循环，也避免只信任可以一起被改写的旁边 checksum 文件。路径、类型、符号链接、身份或摘要不符必须在容器及数据卷操作之前拒绝。该校验不是签名：执行入口前仍需从可信发行渠道确认入口或整包摘要。

构建端仅消费显式预构建制品，生成过程不连接 Docker 或数据库。生成入口的确定性、实际 shell 校验、篡改拒绝、平台选择和文件安全由独立 Check 验证；真实安装、切换、恢复和删除继续由完整发布验收覆盖，不用生成脚本成功代替容器运行证据。

#### 1.6.9.2. 私有安装与更新恢复操作

`LF-TSK-OPS-2011` 负责私有安装状态和 Docker 资源适配，预计 90 分钟，前置 OPS-2010 与 OPS-2006。它和 OPS-2007 顺序交付同一生成入口；状态/锁及精确资源归属与更新指针切换分别验收，不增加产品业务进程。

用户显式指定私有 installation root。入口在该目录记录安装身份、完整发行组合及 active/previous/candidate，不接管未知目录。`prepare` 对已存在目录先只读核对 owner/state 与 engine 记录，失败返回固定 `LF_INSTALLATION_UNVERIFIED`，不查询 Docker、不写入或删除安装目录。用户保留原目录，确认操作停止后选择未占用的新私有路径重试；此诊断不证明残留目录归属，也不承诺同路径自动恢复。凭据由系统随机源生成，仅写入本安装私有文件。每个组合拥有独立 Compose project、资料卷与标签，启动前校验本机引擎、镜像平台及不可变 image ID。Docker 端点选择先读取显式 `DOCKER_CONTEXT` 对应的本机元数据；无 context 覆盖时使用 `DOCKER_HOST`，否则读取当前 context。只接受绝对 Unix socket，拒绝 TCP/SSH、相对路径与控制字符；后续 Docker/Compose 命令显式绑定已选端点，并在子 shell 清除 host/context/TLS 覆盖值，不更改用户配置。Compose 不继承用户的环境文件或项目覆盖值。 自定义归属标签仅使用 `lexiflow.installation` 和 `lexiflow.release`；`com.docker.compose.*` 保留标签由 Compose 生成，不能在 YAML 手工声明。

Docker CLI 包括 context 探测均经过固定预算的命令执行器：普通命令 30 秒，仅固定资料初始化操作 600 秒。输出在本次独占私有目录捕获，以文件写入限制控制两条流；成功输出阈值每流小于 256 KiB，失败不回显原始输出。超时或 timer 工具失败终止本次 CLI，回收本次 timer；不接受用户环境中的预算或 PID 覆盖。命令级超时不是整套初始化/冷启动资源验收，也不证明 Docker daemon 已取消接收的操作或 Compose plugin 后代已退出；结果不确定时保留 journal，通过恢复流程处理。

更新按 prepare → activate 执行：先在独立空间初始化资料并验证无宿主端口的候选 API，成功后才写切换 journal、停止旧服务并启动新服务。新服务实际健康后提交活动指针；失败恢复完整旧软件和数据库组合，不在旧库执行重建。中断或结果不确定时保留 journal，使用 recover 恢复；状态写入失败不能先停止旧服务。稳定运行时只保留一份恢复空间，另一次更新前需显式删除不再保留的那份，不自动删除恢复数据。

更新尝试失败，即使已恢复原安装，也必须返回非零；无法确认候选服务已经停止时，不得启动旧服务或写入稳定状态。停止与重新启动分别先写 `stopping`、`starting`，成功后才写 `stopped`、`idle`；`activate` 只可重启调用入口自身对应的活动发行。重复准备同一已准备/活动发行不得再次初始化资料，中间状态须按对应重试或恢复流程处理。内部跨发行委派同时绑定入口自身 release key、记录摘要和当前锁，拒绝错误入口递归委派。

资源归属检查覆盖 prepare、start、stop 和临时候选清理，不只在删除时执行。每次 Compose 变更前先按项目名和标签发现全部容器、网络及卷，核对固定名称、完整 ID、project/installation/release 三项归属及当前锁；成功后再核对归属，发现错误立即停止后续动作。同名但缺少标签的对象不能接管，发现失败不等于不存在。初始化容器使用固定名称；重试时仅按完整 ID 停止并清理本发行遗留的候选/初始化容器，确认实际已停止后才删除，不触碰 API、PostgreSQL 或资料卷。健康观察也绑定已核对的完整 ID，拒绝名称被替换或已停止的容器。

stop 按完整 ID 停止本发行的服务和临时容器，不广播 Compose stop、不删除卷；每项停止后核对实际状态，最后再次发现并确认没有新身份或仍运行的容器。delete 需要完整 release key 与明确的数据删除确认。删除适配器先完整核对全部资源，再逐项重验锁与归属并删除，容器/网络按完整 ID、卷按精确名称操作。未知资源、发现失败或标签错配均拒绝；删除中断保留 journal，删除后再次确认集合为空，不把部分清理当作完成。不使用 `down --remove-orphans`、全局 prune，不删除共享镜像或清理扩展偏好。独占锁不依据 PID 自动拆除；只有用户确认旧操作全部结束后，才可使用精确 token 明确解除被放弃的锁，正常流程不自动解除。

私有密码只接受普通非符号链接、权限 `0600`、恰好 64 字节的小写 ASCII 十六进制内容。生成时先写同一发行目录的固定私有暂存文件，完整校验并重新核验安装锁与发行记录后，以不覆盖已有文件的硬链接发布；不向最终密码路径直接写入半成品。持锁重试仅清理合同内的普通 `0600` 暂存文件，已有合法密码保持不变；已有畸形密码、错误权限或未知文件类型拒绝。清理失败仍返回失败，保留完整密码供相同入口重试；删除流程将这两个固定暂存名纳入精确文件集合，仍最后删除发行记录。该机制不替代首次安装目录创建的中断恢复。

删除的文件收尾也必须可恢复：资源确认清理后，将匹配发行记录和秘密所在目录原子转移到本安装的固定删除暂存目录（tombstone），提交移除该发行指针的状态后，才按固定文件集合清理。中断后以相同 key 和确认词继续，不因普通记录缺失就推断资源已清空；未知条目、符号链接或身份冲突阻断。记录最后删除，非空且丢失记录的暂存目录不得自动清理。用户下载包、安装根和浏览器偏好不在此删除范围内。

确定性 Check 实际运行生成入口和合成 Docker 状态夹具，覆盖故障顺序及本机文件安全；真实容器 Check 独立执行。后者缺 Docker Compose、受控测试 lease 或发行资料时必须 BLOCKED，不能静默改跑夹具。两种检查均不等于当期平台性能或正式许可验收。

#### 1.6.10.1. 构建输入与候选产物

`prepareImageBuild` 校验干净源码、统一版本、预构建 JAR 和固定 Docker 上下文模板。基础镜像分别声明 registry manifest digest 与本地 image ID，不混用。当期选取 arm64，API/PostgreSQL 两项配置必须完整；路径、未知字段、镜像引用或摘要不合要求时不产生构建计划。计划为固定 argv 数据，不执行 shell 字符串，不含本机绝对路径或凭据。

候选构建与正式发行分开。构建前须确认实际引擎、镜像平台及基础运行时，构建后才能取得最终 image ID 和导出摘要。模拟构建、调用者声明的 `verified` 或局部测试通过均不能代替实际启动验收；缺许可或受控运行环境为 BLOCKED。

`buildCandidateImages` 接受源码、制品输入、输出父目录、Unix Docker endpoint 和 `platform`。每次仅构建所选 `linux/amd64` 或 `linux/arm64`，执行前核对实际 Linux daemon 架构，不匹配拒绝。它创建私有候选目录与空 Docker 配置，不继承开发者凭据或远端 context；核对基础镜像引用、image ID、OS 与架构后复制六个固定上下文文件并构建导出。确定性摘要 `buildInputSha256` 连同软件、源码、平台和文件摘要写入候选记录。失败只清理本次目录，不删共享镜像或用户数据。Docker 子进程固定参数、有限输出和超时，不执行 login/push；`--network=none` 仅限制 Dockerfile RUN 网络。候选记录不是完整发行包或正式验收 receipt。

`assembleReleaseCandidate` 要求 `imageCandidates` 与 `descriptor.platforms` 一一对应，每份指定安全目录 `directory` 和候选记录 `sha256`。记录须覆盖不同平台，绑定同一干净源码与软件版本，具有相同构建输入摘要。装配器按平台流式复制镜像及资料包、扩展、SQL、Compose 与许可文件，调用生命周期入口生成器和清单装配器。输出 `payload/` 含待验收制品，外层 `candidate.json` 绑定清单、构建输入及候选摘要；全部原始输入重验成功后才生成标记。摘要须来自受控交接，不信任随文件附带的 checksum。

**Check 冻结**：`eng.release.build` 冻结构建入口、执行器、候选装配、直接测试及校验器、Docker 模板。测试不运行 Docker，不签发平台支持证明。`eng.release.lifecycle-runtime` 冻结全部构建声明输入；构建/装配/模板变动必须选中真实运行检查，构建测试通过不覆盖运行检查的 FAIL/BLOCKED。

#### 1.6.10.2. 构建机命令入口

发行构建机使用固定命令串联两个步骤；普通安装使用者不执行这些命令，也不需要 Node。

```sh
node ops/release/pipeline.mjs images /absolute/images-request.json
node ops/release/pipeline.mjs assemble /absolute/assemble-request.json
```

在各自匹配的平台构建机执行一次 `images`，固定两份候选摘要并完成受控交接后，才填写并执行 `assemble`。两个请求都是普通 JSON 文件，最大 2,000,000 字节，文件及祖先不能是符号链接；路径必须绝对。命令拒绝未知模式、额外参数和自定义 runner/argv，不执行 shell 字符串。

| 模式 | 请求顶层字段 | 输出和下一步 |
| --- | --- | --- |
| `images` | `repoRoot`、`artifactRoot`、`descriptor`、`outputParent`、`endpoint`、`platform` | 输出的 `candidateDirectory` 和记录摘要作为装配请求的一项 `imageCandidates` |
| `assemble` | `repoRoot`、`imageCandidates`、`artifactRoot`、`descriptor`、`outputParent` | 两平台候选齐备后装配，输出目录的 `payload/` 进入受控运行验收，不直接发布 |

两种 `descriptor` 分别沿用构建输入与完整制品清单合同；不互换，不省略基础镜像、许可和制品摘要。输出父目录须预先存在且在输入目录之外。请求只在构建机保存，不包含账号凭据；失败时保留原输入，按固定错误码核对参数、请求文件或底层构建条件，不自动重试或清理他人的目录。

命令退出零且单行 JSON 为 `status=PASS`、`scope=candidate-only`，只表示该候选步骤完成。`candidateDirectory` 是本机目录定位，不是正式发行地址；不得把它当作当期平台启动、许可或 Formal Gate 的验收证据。失败退出 1，返回固定错误码，不回显请求正文、底层异常或错误路径。
