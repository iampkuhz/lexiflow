## 1. 目标与交付边界

LexiFlow 的首个产品入口是 YouTube Chrome 扩展。英文字幕必须立即显示，系统只对用户可能不熟悉的词、短语和专业术语增量补充结合语境的中文提示。后端维护跨设备共享的个人词汇档案，并通过可回放的学习归约事件持续更新熟悉度。

项目采用 **模块化单体**。部署可以是单体，代码和数据所有权必须按领域分开。第一版允许 PostgreSQL、Redis、API、工作进程和 Chrome 扩展；在真实负载证明必要前，不引入 Kubernetes、Kafka、服务网格、向量数据库或微服务拆分。

当前只授权推进 `P1 Architecture`。`P2` 到 `P7` 在本计划中用于建立依赖、容量和长期拆分边界；它们在 `G1` 获得用户明确认可前不得进入实现。P1 的输出停留在领域、职责、依赖方向、核心数据流和同步/异步边界，不提前冻结表字段、REST 端点、Compose 文件、提示词或实现代码。

## 2. 设计原则

1. **英文优先且不阻塞播放**：英文字幕走同步快路径；提示注释可异步增量到达。
2. **后端是个人学习状态真源**：扩展只采集、渲染、缓存和上报，不拥有最终个人词汇档案。
3. **规则决定是否帮助，模型决定如何解释**：规则、词典和用户画像先筛选；模型只处理消歧、术语、短语和中文表达。
4. **事件先于派生状态**：学习归约事件不被最终熟悉度覆盖；画像可按新算法重放。
5. **抽象提供者**：业务代码依赖 `SemanticProvider` 能力，不依赖某个厂商 SDK。
6. **证据决定完成**：进程退出、代理声称完成或回调成功都不等于验收通过。
7. **逐层冻结**：每个阶段先呈现总体方案、核心决策、2–3 个替代方案、取舍和推荐，再由阶段 Gate 决定是否展开下一层。
8. **扩展入口复用核心**：YouTube 是第一个内容适配器；网页、PDF、播客和其他视频平台复用内容、提示编排、学习归约与个人词汇。

### 2.1 从参考仓库继承的工程约束

本计划复用 `/Users/zhehan/Documents/tools/llm/feipi-session-browser-java` 中已经证明可维护的结构原则：业务核心、应用层、端口/SPI、适配器、网页/CLI 入口分层；逻辑模块 ID 与物理目录解耦；架构、合同、quality-gate 测试分层；`harness` 只保存静态机器契约；Gate 先编译唯一计划，再执行负责人，最后保存不可覆盖收据；平台配置只做入口，不保存项目运行状态。

这些原则会映射为 LexiFlow 的领域模块、内容/语义端口、API/工作进程/扩展适配器、`planning`/`harness` 真源和显式增量 Gate。参考仓库的会话专用模块、SQLite 选择和 JDK 版本不会直接复制；LexiFlow 的语言、构建工具、PostgreSQL/Redis 适配和部署形式仍由 `G1` 的技术栈 ADR 根据本产品负载决定。

模块依赖必须按下列方向实现：组合根同时组装应用层与具体入站/出站适配器；入站适配器调用应用层；出站适配器实现领域端口；应用层只依赖领域/端口。`application -> concrete adapter`、`domain -> framework/database/cache/provider` 和入站适配器直接调用出站适配器均为禁止边。组合根是唯一知道具体实现并完成装配的位置。

## 3. WBS 与稳定身份

### 3.1 五层结构

| 层级 | 含义 | ID 格式 | 是否可直接派发 |
|---|---|---|---|
| 长期计划 | 一个长期产品投资 | `LF-PRG-001` | 否 |
| 大型能力组 | 一个稳定业务域或横切能力 | `LF-EP-{DOMAIN}-{NNN}` | 否 |
| 能力 | 可验收的用户/系统能力 | `LF-CP-{DOMAIN}-{NNN}` | 否 |
| 任务 | 单负责人、单目标、可独立验收的最小计划单元 | `LF-TSK-{DOMAIN}-{NNNN}` | 是 |
| 运行 | 某个任务的一次设计、实现、复核或返工尝试 | UUID，展示别名 `{task_id}-R{NNN}` | 是 |

`DOMAIN` 使用 `planning/workstreams.yaml` 中登记的代码。ID 一旦分配不得改义、复用或因阶段迁移而重编号。阶段、优先级、里程碑和状态都是可变属性，不编码进 ID。删除的 ID 保留为 `retired`；替代关系使用 `supersedes`/`superseded_by`。

### 3.2 规模扩展方法

`workstreams.yaml` 是种子目录，不为未来几百个子功能创建空文件。扩展时按以下方式增长：

- 能力表示业务能力，不等于实现任务。一个能力通常激活为 3–12 个可独立验收的原子任务；每个任务可产生设计、实现、定向测试、独立复核、Gate 验证和返工运行，但这些运行不得被计作新的子功能。
- 目录中的种子任务提供主干。进入某阶段前，对该阶段 P0/P1 能力做按需分解，并把新任务写回同一目录或后续机器目录。
- 当前目录已登记 18 个工作流、41 个能力和 113 个真实原子任务，其中 8 个 Gate 控制面任务是经过设计与独立评审后激活的 JIT 任务。后续按能力的实际缺口新增 262 个原子任务，形成 375 个完全展开容量目标；300 个任务是项目规模基线。基线公式为 **300 任务 × 5 运行/任务 = 1,500 运行**；上界公式为 **375 任务 × 8 运行/任务 = 3,000 运行**。这里的运行是任务级设计、实现、测试、复核、Gate 或返工证据，不是子代理会话；工作包按共享策略聚合多个任务和运行。
- 只有真实目标、负责人、依赖、交付物和验收均已明确时才创建任务。运行是执行历史，不能用复制空任务的方式制造规模。

按阶段的完全展开容量范围由机器目录校验：

| 阶段 | 当前种子 | JIT 可新增 | 完全展开目标 | 主要容量来源 |
|---|---:|---:|---:|---|
| P1 | 32 | 13 | 45 | 架构、边界、Harness、Gate 控制面、威胁与性能预算 |
| P2 | 14 | 36 | 50 | 数据模型、事件、词库、个人档案与迁移 |
| P3 | 13 | 37 | 50 | API、鉴权、同步、事件入口与合同测试 |
| P4 | 23 | 57 | 80 | 提示编排处理流程、语义供应商、缓存与质量基准 |
| P5 | 11 | 49 | 60 | YouTube 适配器、叠加层、离线恢复、浏览器 E2E 与可访问性 |
| P6 | 8 | 37 | 45 | 学习归约评分、重放、投影、跨设备闭环与对比验证 |
| P7 | 12 | 33 | 45 | 安全、观测、容量、灾备、发布与未来适配器验证 |
| **合计** | **113** | **262** | **375** | `planning/workstreams.yaml.phase_capacity_budget` |

容量范围用于证明项目能够稳定扩展，不是 Gate 的机械最小任务数。Gate 只检查当前已激活的范围完整、没有空壳、P0/P1 和风险覆盖充分；低于范围是正常的 JIT 分解状态，只需记录差异、理由和覆盖证据，不需要用户为正常差异额外批准。不得为追平 375 机械生成空壳 ID。

## 4. 拆分与调度规则

<a id="41-task-的准入条件"></a>

### 4.1 任务的准入条件

一个任务同时满足以下条件才进入 `READY`：

- 一个可验证目标，完成标准能在 1–5 条断言中表达；
- 一个主要负责人和一个写入范围；实现与其直接测试同任务交付；
- 硬依赖均为 `PASS`，所消费的合同版本已固定；
- 每个独立任务预计 20–90 分钟；
- 包含真实验证命令或明确的人工证据格式；
- 风险、回滚/降级方式、禁止修改范围已声明；
- 没有与运行中任务重叠的文件声明。

出现任一情况必须继续拆分：跨两个限界上下文、跨两个文件负责人、同时改变供应商合同与两个以上消费方、超过 8 个主要生产文件、需要互不相关的验收环境、或预估单任务超过 90 分钟。纯重命名/格式化可以批量处理，但不得借机混入行为变化。

同一领域内的紧密步骤可保留为运行检查清单；发现独立目标、不同负责人或新的风险边界时，分配新的任务 ID，并用 `discovered_from` 和 DAG 边连接。不得在运行内暗中扩大任务范围。

原子任务不直接等同子代理调用。工作包聚合、模型选择、并发与回调只遵守[共享调度策略](../../harness/agent-policy.manifest.yaml)，本页不保留可漂移的副本。

### 4.2 依赖 DAG

- 只允许 `Task -> Task`、`Capability -> Capability` 的 `depends_on`；DAG 必须无环。
- 每条种子依赖都是对象，至少固定 `task_id`、`type`、`required_task_version` 与 `required_change_version`。`hard` 还要求 `required_result=PASS`；`soft` 只影响排期；`contract` 额外固定 `contract_name` 与 `required_contract_version`。
- 公共结构定义/API/事件/供应商合同先由负责人任务冻结，消费方任务才能并行。
- 集成任务依赖所有贡献任务；发布 Gate 依赖集成与独立验证任务。
- 禁止用阶段序号隐式表达依赖。跨阶段提前做风险验证时，必须显式挂在已满足的任务上。
- P2–P7 的每个入口任务必须直接建立硬依赖于上一 Gate 退出任务，并声明上一 Gate 为 `PASS`、退出任务/变更版本精确匹配、用户批准为 `APPROVED`。验证器还必须证明同阶段其他任务的阻断祖先链可追溯到合法入口，且阶段退出任务覆盖全部 P0 入口。

<a id="43-文件-owner-与并行写入"></a>

### 4.3 文件负责人与并行写入

`workstreams.yaml.path_ownership` 是负责人真源。架构 Gate 前使用逻辑范围；Gate 通过后绑定为实际路径。解析负责人时使用“最具体范围优先”。

负责人表必须覆盖产品路径，也覆盖当前治理入口：`docs/development/**`、`docs/reviews/**`、`docs/references/**`、`openspec/**`、`.codex/**`、`.qoder/**`、`AGENTS.md`、`README.md`、`.gitignore`、`docs/README.md` 与 `scripts/README.md`。Chrome 扩展的唯一 protected/负责人路径为 `clients/chrome-extension/**`。

- 一个文件在同一时刻只能被一个任务声明。
- 并行修改型代理的 `allowed_files` 不得重叠；共享合同由合同负责人串行落地。
- 其他负责人通过消费方任务适配，不直接越界编辑。
- 生成物和运行凭证写入每运行唯一目录；不得共用可覆盖的 `latest` 作为验收真相。
- 集成、迁移顺序、发布清单和最终 Gate 串行执行。

## 6. 状态、证据与质量 Gate

### 6.1 计划状态与验收状态

计划生命周期使用 `DRAFT -> READY -> DISPATCHED -> IN_PROGRESS -> REVIEW -> DONE`，并允许 `BLOCKED`、`SUPERSEDED`、`CANCELLED`。它与验收结果分开：

| 验收状态 | 含义 |
|---|---|
| `PASS` | 必需验证完整执行且全部通过，证据可定位 |
| `BLOCKED` | 验证完整执行并发现产品、规则或测试阻断 |
| `FAIL` | 输入、依赖、环境、超时、中断或不可判定导致验证未有效完成 |

`skipped`、`not-run`、`unavailable`、`excluded`、代理零退出码、任务已回调或通知 queued 都不得描述为 `PASS`。

<a id="62-每个-run-的最小证据"></a>

### 6.2 每个运行的最小证据

- 精确任务/版本、代理/客户端/父级会话、开始结束时间；
- 变化的文件与文件声明对账；
- 验证命令、退出码、stdout/stderr 摘要和不可覆盖日志路径；
- 验收条件到自动化测试、人工检查或观测指标的映射；
- 效果检查：预期行为、回归面、性能、安全、隐私和数据迁移影响；
- 风险、遗留限制、回滚或降级入口；
- 主代理的独立复核结论。

Gate 的机器计划必须先冻结输入，再给出 `file -> trigger -> gate` 原因；执行产生唯一收据。Gate 聚合顺序是 `FAIL > BLOCKED > PASS`。

## 7. 版本变化与返工

- `task_id` 稳定，`task_version` 使用整数递增；运行永远引用精确版本。
- `change_version` 使用 SemVer：文字澄清且不改验收为补丁；新增兼容范围或验收为次版本；改变目标、合同或破坏兼容为主版本。
- 已 `DISPATCHED` 的任务不得原地改范围。先将旧版本标为 `SUPERSEDED`，保存原因，再派发新版本。
- 合同变更必须列出受影响消费方、兼容期、迁移任务和回滚策略；依赖边随版本更新。

<a id="8-phase-17-与阶段-gate"></a>

## 8. 阶段 1–7 与阶段 Gate

阶段不是简单瀑布：风险验证可以提前，但任何执行都必须遵循 DAG。P2–P7 的入口由上一 Gate 退出收据与明确的用户批准收据双重控制；缺一项时任务不能进入 `READY`。每个 Gate 均要求：总体方案、核心决策、2–3 个备选、取舍、推荐、未决假设和用户明确结论。

<a id="p1--architecture"></a>

### P1 — 架构

交付领域映射、模块职责、依赖方向、两条端到端数据流、同步/异步边界、可靠性预算、逻辑文件负责人和关键 ADR。重点决策包括模块化单体边界、事件保留方式、供应商抽象、扩展/后端真源边界和缓存一致性。

`G1 Architecture Accepted` 通过条件：

- 六项架构交付均有可审查文档；
- 依赖图无环，领域不反向依赖适配器/infrastructure；
- 提示注释快路径与学习归约事件路径标明同步/异步、超时和兜底；
- 关键选择均有 2–3 个备选与取舍；
- 用户明确认可方向。

<a id="p2--data-model"></a>

### P2 — 数据模型

在 G1 后设计 PostgreSQL 结构定义、事件模型、词库、个人词汇档案、内容、提示注释、索引、保留与迁移。先冻结概念和不变量，再进入字段与迁移脚本。

`G2 Data Contract Accepted` 要求结构定义/版本演进、事件幂等、重放、租户/用户隔离、索引假设和迁移回滚均有证据。

<a id="p3--api"></a>

### P3 — 服务接口

设计提示编排、个人词汇、事件、鉴权、客户端同步、错误模型、幂等与版本演进。合同测试先于消费方并行实现。

`G3 API Contract Accepted` 要求 OpenAPI/等价契约、兼容策略、授权矩阵、幂等与错误语义通过合同测试。

<a id="p4--enrichment-engine"></a>

### P4 — 提示编排引擎

按规范化、令牌/短语检测、词典/个人词汇查询、候选生成、提示需求、消歧、翻译、提示注释分层实现。规则与模型的责任不得混合为单次整句翻译调用。

`G4 Enrichment Quality Accepted` 要求离线标准样例集合、上下文消歧、提示稀疏度、供应商兜底、缓存键正确性及 P95/P99 预算达标。

<a id="p5--chrome-extension"></a>

### P5 — Chrome 扩展

实现 YouTube 字幕获取、播放器上下文、叠加层渲染器、API 集成、L1 缓存、事件集合、重连/回退与权限最小化。

`G5 End-to-End Experience Accepted` 要求英文零等待显示、提示注释增量渲染、播放器状态适配、断网降级与浏览器自动化用例通过。

<a id="p6--learning-model"></a>

### P6 — 学习归约模型

先交付可解释规则/评分，再引入概率熟悉度。事件到个人档案的推导必须版本化、可重放、可对比和可回滚。

`G6 Learning Loop Accepted` 要求跨设备事件合并、画像更新、算法重放、解释输出与用户 known/unknown 反馈闭环通过。

<a id="p7--productionization"></a>

### P7 — 生产化

完善部署、可观测性、安全、备份/恢复、速率限制、模型成本、负载测试、性能调优和发布/回滚。生产能力按切片提前嵌入各阶段，P7 完成系统级收口。

`G7 Release Ready` 要求安全与隐私审查、灾备演练、成本上限、SLO、容量和发布回滚全部有不可覆盖证据。

| MVP | 单用户在 Chrome/YouTube 上看到英文字幕与少量语境中文提示；行为可上报，个人档案可跨浏览器同步 | G1–G5；G6 的解释型基线切片；G7 的本地/单环境部署、安全、日志、备份最小切片 | 概率模型、多内容源、团队协作、高可用 |
| Alpha | 邀请用户使用；个人档案跨设备稳定；缓存、供应商兜底、事件重放和成本观测可用 | 全部 P0 与目标 P1 任务；G6；G7 的告警、限流、恢复演练 | 大规模增长和自动 ML 训练 |
| Beta | 可控外部用户；隐私、可恢复性、兼容升级、容量与支持流程达到发布标准 | G1–G7；所有发布阻断风险关闭；全量回归/负载/安全 Gate | 微服务/K8s 等无负载证据的扩展 |

里程碑是能力切片的集合，不复制任务。任务用 `milestone_slices` 标明归属，一个任务可服务多个里程碑。

## 10. 优先级与风险

| 优先级 | 定义 | 调度规则 |
|---|---|---|
| P0 | 当前 Gate 或里程碑不可缺少，涉及真源、核心路径、安全/数据完整性 | 硬依赖满足后优先；阻断则 Gate 为 BLOCKED |
| P1 | 显著影响质量、性能、可运维性或主要体验 | 目标里程碑前完成 |
| P2 | 改善效率或边缘体验，有明确降级 | 不阻断 MVP/Alpha，按容量调度 |
| P3 | 探索性或未来入口 | 只有证据触发，默认不展开 |

要求等级映射为 `MUST`、`SHOULD`、`CAN_EVOLVE`，不代替优先级。风险按影响 × 发生可能性分为 low/medium/high/critical；high/critical 任务必须有独立审阅者、失败降级和专门验证运行。
