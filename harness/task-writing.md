# 1. 任务卡编写规范

在 Multica 写卡时，先区分用途：版本汇总卡让读者快速了解本版交付；可执行任务卡让接手者知道要改什么、如何验证。编写规则以本页为准；拆分、派发和正式验收按[协作规则](agent-policy.md)执行。

## 1.1. 版本汇总卡

- **标题用明确的目标版本号。** 格式为 `LexiFlow vX.Y.Z｜研发与交付汇总`。版本未定时先确认，不用「下一版」、日期或开发分支代替版本号。
- **维护本版开发分支。** 每个版本指定唯一集成分支，命名采用 `codex/vX.Y.Z-development`，按发行版本号命名，不使用接口协议号。汇总卡正文开头写「开发分支：」，改名时同步更新。子 Issue 沿用汇总卡的分支；分支名不代替实际目录核对，也不授权切换或派发。
- **在汇总卡集中写本版的开发上下文。** 在开发分支旁写明本版使用的 Multica 项目目录资源，并指向仓库 Harness。实际路径以项目资源绑定为准，子卡只指向父卡，不复制路径和分支。目录核对与工作区例外见[版本开发目录与清理](agent-policy.md#版本开发目录与清理)。
- **正文先总后分。** 「版本目标」用一句话说清本版交付意图。「核心改动」每项一句，写清对象和变化；只扫这一节也能看懂。「改动详情」按同一编号与顺序展开，只补行为、影响和限制，不复述摘要。
- **按需补充「发布影响」和「待决事项」。** 有本版特有的升级前提、用户操作或适用限制才写「发布影响」；有会改变本版范围、交付或升级的决定才写「待决事项」。没有实质内容就省略。
- **正文保留读者需要的技术细节。** 分支名、提交号、内部字段及实现代号不进摘要；需要追溯时在对应条目关联子 Issue、OpenSpec 或 PR。不要把观察到的开发改动写成已验收或已发布。
- **不另设通用「验收与收口」或「执行约定」。** 逐项验收条件写在对应任务卡的需求评论里；实际验证、发布结果和证据按需回填关联入口，不复制仓库规则或原始日志。

### 1.1.1. 版本汇总卡样例

标题：`LexiFlow vX.Y.Z｜研发与交付汇总`（填入已确认版本号）。

```markdown
**开发分支：** `codex/vX.Y.Z-development`
**开发目录：** 项目 Resources 中为本版指定的固定本机目录（`in_place`）。
**执行规则：** 仓库 `AGENTS.md` 与其指向的 Harness。

## 1. 版本目标

让用户在弹窗中查看当前视频的词汇提示及实际展示次数，同时简化本机部署。

## 2. 核心改动

1. 扩展弹窗新增当前视频的词汇列表。
2. 本机部署固定正式和测试两个容器槽位。

## 3. 改动详情

1. **词汇列表**：展示词频名次、英文、中文短释和实际展示次数；换视频后清空。
2. **本机部署**：更新和回退复用原槽位并保留数据卷，自动验收使用隔离环境。

## 4. 发布影响

扩展与服务须使用配套版本。
```

## 1.2. 可执行任务卡

- **标题写对象和预期变化。** 围绕同一目标、落在同一修改范围的需求可以分轮放在一张卡；可独立交付和验收的结果按[工作范围与分解](agent-policy.md#工作范围与分解)拆卡。属于某版时关联版本汇总卡，不重复整版说明。
- **Description 只写长期有效的信息。** 写清卡片目标、范围与不做什么，并说明具体需求见评论。不把首轮需求或后续逐项改动、验收条件在正文再维护一份；只有卡片目标或边界本身改变时才改正文。
- **首轮和后续需求都写评论。** 一组同范围需求发一条顶层评论，标明「首轮需求」或「追加需求」；对同一条的澄清回复其线程。写清现象或最短复现、预期与可观察的验收条件。修订既有要求时注明替代哪条；有冲突且未明确取舍时，开工前先确认。
- **记录需求和授权开工分开。** 仅登记可用 `/note`，不 @ 派发；开工时核对 Description、相关需求评论及回复，明确本次做哪些条目，不把整段讨论都当成执行指令。通用检查、角色权限和发布授权不复制进卡；证据用合成样例或脱敏材料，不上传真实字幕、观看历史或本地运行资料。

### 1.2.1. 可执行任务卡样例

标题：`修正词汇弹窗窄宽下的三列对齐`（格式示例，不代表已发现缺陷）。

Description：

```markdown
## 1. 目标

让词汇弹窗在窄宽下仍易读、可操作。

## 2. 范围

只调整词汇列表排版，不改计数规则、字幕叠层或后端接口。首轮和后续同范围需求见评论。

**执行上下文：** 本版父卡与仓库 Harness。
```

首条评论（仅登记）：

```markdown
/note

**首轮需求｜窄宽下三列对齐**

- **现象**：窄宽下，长英文、无名次或多位数次数可能让列错位或遮挡控件。
- **预期与验收**：用合成数据覆盖长英文、无名次、0 次和多位数；窄宽与常规宽度下，英文起点对齐、次数右对齐、释义可换行且列表无横向滚动。
```

## 1.3. 从 Codex 登记需求

1. **先收问题，不要求编号。** 用户可以直接描述现象和预期。Codex 核对当前研发版本及其汇总卡；版本或需求范围不明确时，先问清楚。普通咨询不改卡。
2. **先按范围查重。** 检查该版本汇总卡下的子 Issue，核对 Description 的目标和边界，以及相关需求评论的内容，不能只凭标题或关键词匹配。范围一致就复用原卡；没有匹配项才新建未指派的子 Issue。已关闭的卡不自动重开，不把新需求塞进范围不同的旧卡。
3. **同一入口登记。** 新卡先写 Description，再把首轮已知需求发成评论；复用时只追加未记录的同范围需求。用户在 Codex 口述与在 Multica 直接评论，最终都以卡上的需求评论为准，不要求用户再抄一次。
4. **登记后先回报，不开工。** 告知用户复用或新建的卡号，以及本次登记的范围；不改代码、不派发。等用户明确要求开工，再按协作规则核对执行目标。

## 1.4. 在 Multica 触发执行

- **只做本轮：在对应需求评论下回复 `@Agent 开工`。** 从候选列表选中实际 Agent，不加 `/note`。默认只做该线程已明确的需求；只做部分时写「只做第 2 项」即可。不会更改整张 Issue 的 Assignee。发送前核对触发预览；发送后看 Run，已排队不等于已开工，不重复触发。
- **整卡交给 Agent：设置 Assignee。** 只有需要 Agent 持续负责整张 Issue 才指派，先看操作是否会启动 Run；若已经启动，不再用评论重复触发。仅登记或讨论用 `/note`，不授予开工权限。
- **固定内容不写进触发回复。** Agent 从触发线程和子卡读取本轮需求与边界，从父卡取目标分支和目录资源，按 `AGENTS.md` 与 Harness 核对实际目录、分支和写入归属；缺失或不符时在原线程报告 `BLOCKED`。完成后在原线程说明改动和验证。开工不包括 Git 集成或发布授权。
