# 1. 正式单容器发行

## 1.1. 两步使用与环境前提

在 macOS Apple Silicon、Podman 已安装并运行、Chrome 已安装的前提下，只需执行该 Release 明确软件版本 tag 的一条 `podman run` 命令，以及下载解压并启用同版本扩展。用户不获取源码/主安装归档，不安装语言工具链、Compose 或外部数据库，不配置密码、地址、卷或词库。Podman安装启动不计入两步。

正式使用 `lexiflow-release`/18080/`lexiflow-release-data`，开发调试18081和独立数据，验收18082和唯一归属临时资源；不得接管、覆盖或删除未知资源。只暴露宿主loopback API，SQLite 数据库文件不映射宿主。

## 1.2. 镜像与持久化

新正式发行只有 `ghcr.io/iampkuhz/lexiflow` 一个用户运行镜像，唯一 `linux/arm64` 运行容器包含Java25、SQLite JDBC运行时、专属数据库文件、已发布词库及离线初始化能力。唯一Java产品应用不新增worker；基础设施进程管理不使用特权、socket或容器套容器。

同一run命令自动建立命名卷，识别归属/格式，事务初始化，重新启动验证实际数据库包与镜像期望。初始化标记与成功标记分开；关键组件/初始化/资料验证失败不能报告正式健康。未知非空或不兼容卷拒绝且保留数据，不承诺任意历史数据库迁移，不静默清库。

API的最新status包含真实初始化状态及 `publishedDataset` 五字段绑定（releaseId/preparationId/ruleId/sqlVersion/sha256）。只有本次boot已验证实际数据库包且实时发布版本匹配才能返回就绪和该绑定。扩展期望、软件版本和API协议均匹配；后端不可用或不兼容时英文继续，本机偏好不上报，观看不调用模型。

## 1.3. 发行身份和制品

私有候选唯一 `runtime-image`，固定 archive 路径 `images/linux-arm64/runtime-image.tar`，完整绑定源身份、资料、SQL、扩展和许可。通过真实独立Formal前不推公开GHCR；晋升仅原制品，版本不同内容拒绝，不重构建覆盖。

用户Release自定义附件恰好扩展ZIP、对应源码包、`release.json`，不上传内部candidate、主安装tar、镜像tar或独立checksum。原批准材料及来源/摘要/对应关系完整保留，运行镜像有必要告知，源码聚合包assemble时生成并受验。机器只读不可变release.json；正文从对应提交的版本说明生成，缺失/空白/版本错在写前拒绝。页面只保留用户可见变化、前置条件、两步使用和数据限制，自动补真实下载链接及明确软件版本 tag 命令，不使用 latest；摘要、digest 与完整身份仍由 release.json 承载，tag 不替代内容身份。

人工说明使用唯一模板，严格包含本版变化、两步使用、数据与限制三个有序非空章节；缺失、重复、占位符和版本不一致在远端写入前拒绝。本版变化不重复产品介绍或内部验证过程。现有只读晋升预检使用实际发布的同一正文生成函数，向维护者入口返回完整 Markdown；安装命令和下载链接只由既有发布链路生成，不新增模板引擎、独立 Gate 或第二套发布入口。

## 1.4. 发布事务和验收

保留来源许可、安全、完整repository-baseline、真实独立validator/reviewer和人类保护批准。GHCR与GitHub Release非原子事务；已上传镜像不能当作发行完成。部分成功和未知写入保留现场，先只读查明；只在相同已验收字节和确定远端状态下恢复，不自动删除或盲目重传。

必须证明干净拉取建卷初始化、单容器无外置DB、扩展自动连接与字幕回归、同卷持久化与中断恢复、冲突/不兼容/拉取失败/组件异常拒绝、全发行身份一致、匿名真实渠道安装，并测量镜像大小/初始化时间/资源。缺运行或清理不确定不得PASS；两代合成测试不替代真实候选和公开安装。

# 2. 源码开发制品

## 2.1. 软件版本槽位

本机 Podman API 镜像 tag 必须仅由 `ops/release/version.txt` 的基础版本派生为小写：`localhost/lexiflow-api:<baseVersion>`。运行镜像内置 SQLite JDBC 运行时，不构建或管理数据库服务镜像。commit、源码摘要、构建 ID、构建日期和安装 ID不得改变同版本 API tag。完整构建身份必须继续通过制品内嵌资源、镜像 label、安装状态与实际 image ID 核验；tag 不能替代内容身份。

## 2.2. 精确重装

用户确认的 `install` 和 `upgrade` 必须重新准备应用，即使完整构建身份不变。同版本镜像替换前必须核对角色、部署版本和所有引用容器的实际镜像、安装、project、service 归属；先移除本安装容器和精确 tag，再构建或加载。未知归属、其他安装引用、检查失败或漂移必须拒绝，不使用强制删除或全局清理。并发同版本写入由共享非等待内核锁隔离，不删除未知锁。

## 2.3. 数据与失败

SQLite 数据库文件由容器专属持久卷保存，不存在数据库服务镜像、外部数据库目标、账号或凭据。升级/重建前必须停止 API，使用显式离线管理动作并绑定绝对数据库文件与期望摘要；保留数据与成功记录，未知目标、漂移或校验失败均拒绝。资料生成身份保持独立，完整同版本资料可复用。不承诺结构迁移或自动回退旧二进制；未完成准备不能伪装为就绪。计划和拒绝确认不得删除既有部署镜像或容器；准备流程自行创建的一次性来源工具必须精确回收。

## 2.4. 来源工具

来源工具使用仅本次创建者拥有的一次性无 tag 镜像；成功或失败后按完整 image ID 精确清理，不清理其他运行者，不留下持久工具槽位。

## 2.5. 配套插件归档

本机源码 install/upgrade 必须生成与实际 API 完整构建身份匹配的插件 ZIP 与相邻 SHA256 校验和，复用正式发行的确定性打包、文件白名单、身份与归档验证核心。正式发行仍强制干净标签源码与固定 18080 端口；本机允许已确认的有效 API 端口，不允许额外权限。候选安装必须保留已核验的发行 ZIP 原字节。

归档在受管目录 extension-artifacts/<buildId>/ 独占发布，同内容可复用、不同内容拒绝覆盖。安装状态与成功操作记录必须绑定当前归档的路径、字节数、摘要及 API 身份。固定 extension 目录必须由该 ZIP 解压得到，不能另复制任意 dist。准备、激活、就绪与数据库提交后恢复必须核对归档、校验和及对应目录；任何缺失、篡改、身份或端口漂移不签发成功。用户仍需在 Chrome 手工加载／重新加载固定目录，生成归档不表示浏览器安装完成。

## 2.6. 验收场景

- 同基础版本但 commit 或未提交源码变化时，tag 相同、完整身份不同。
- 基础版本变化时 tag 变化；显式同版本重复安装也先移除再构建。
- 其他安装引用、未知角色/版本、并发操作和任意检查失败时，不删除未知资源。
- SQLite 持久数据卷保留；资料生成身份不变且完整时不重导。
- 构建/加载/就绪失败不伪造成功或旧二进制回退；计划不删除既有部署镜像或容器。
- 首次安装、重复安装和 upgrade 均交付配套 ZIP；固定加载目录逐文件等于 ZIP 白名单内容，非默认本机端口一致。
- ZIP、校验和、解压目录篡改与身份不配套必须失败；提交后恢复保持相同验证，未完成不得签发 ready。

## 2.7. 常驻资源与本机健康检查

API 的常驻初始堆与 initialize 的批量导入堆必须分开设置；容器内存上限不代表实际常驻占用。API 数据源使用有界的小连接池，导入专用连接不因此改变。

容器健康检查必须复用唯一 API 进程内的 readiness、正式资料状态与有效软件身份，不为每次检查启动另一 JVM。内部健康端点只接受实际 loopback 连接，不信任转发头；只有接受流量、正式资料已就绪、有效版本且原因属于 OK 或 PREWARM_DEGRADED 才输出固定安全摘要。失败无正文，不泄漏异常或资料。

本机传输必须有共享 deadline 与响应大小上限；拒绝非成功状态、重定向、不完整或不符合固定协议的响应。公开 runtime-status 与 Actuator 端点保持各自合同，降低探针开销不得放松就绪判据。
