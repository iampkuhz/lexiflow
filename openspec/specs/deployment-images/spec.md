# 1. 本机部署制品

## 1.1. 软件版本槽位

本机 Podman API 与受管 PostgreSQL 镜像 tag 必须仅由 `ops/release/version.txt` 的基础版本派生为小写：`localhost/lexiflow-api:<baseVersion>` 与 `localhost/lexiflow-postgres:<baseVersion>`。commit、源码摘要、构建 ID、构建日期和安装 ID 不得改变同版本 tag。完整构建身份必须继续通过制品内嵌资源、镜像 label、安装状态与实际 image ID 核验；tag 不能替代内容身份。

## 1.2. 精确重装

用户确认的 `install` 和 `upgrade` 必须重新准备应用，即使完整构建身份不变。同版本镜像替换前必须核对角色、部署版本和所有引用容器的实际镜像、安装、project、service 归属；先移除本安装容器和精确 tag，再构建或加载。未知归属、其他安装引用、检查失败或漂移必须拒绝，不使用强制删除或全局清理。并发同版本写入由共享非等待内核锁隔离，不删除未知锁。

## 1.3. 数据与失败

托管 PostgreSQL 替换只重建镜像和容器，必须保留数据卷、账号、凭据及数据成功记录。外部 PostgreSQL 不受生命周期管理。资料生成身份保持独立，完整同版本资料复用。删除旧镜像前必须保存绑定安装归属、旧配置/状态摘要、冻结目标与真实数据库 fingerprint 的私有替换记录。失败保留数据与记录，普通交互在再次确认、目标匹配、安装锁及版本锁下恢复本安装托管 PG 的准备能力，用真实 fingerprint 重新计划；目标或其他配置漂移仍拒绝。PG 不可用时计划模式只报告 BLOCKED；外部 PG 不走镜像恢复。不能声称可自动回退同版本旧二进制，也不能由未完成准备伪装为就绪安装。计划和拒绝确认不得删除既有部署镜像或容器；准备流程自行创建的一次性来源工具必须精确回收。

## 1.4. 来源工具

来源工具使用仅本次创建者拥有的一次性无 tag 镜像；成功或失败后按完整 image ID 精确清理，不清理其他运行者，不留下持久工具槽位。

## 1.5. 配套插件归档

本机源码 install/upgrade 必须生成与实际 API 完整构建身份匹配的插件 ZIP 与相邻 SHA256 校验和，复用正式发行的确定性打包、文件白名单、身份与归档验证核心。正式发行仍强制干净标签源码与固定 18080 端口；本机允许已确认的有效 API 端口，不允许额外权限。候选安装必须保留已核验的发行 ZIP 原字节。

归档在受管目录 extension-artifacts/<buildId>/ 独占发布，同内容可复用、不同内容拒绝覆盖。安装状态与成功操作记录必须绑定当前归档的路径、字节数、摘要及 API 身份。固定 extension 目录必须由该 ZIP 解压得到，不能另复制任意 dist。准备、激活、就绪与数据库提交后恢复必须核对归档、校验和及对应目录；任何缺失、篡改、身份或端口漂移不签发成功。用户仍需在 Chrome 手工加载／重新加载固定目录，生成归档不表示浏览器安装完成。

## 1.6. 验收场景

- 同基础版本但 commit 或未提交源码变化时，tag 相同、完整身份不同。
- 基础版本变化时 tag 变化；显式同版本重复安装也先移除再构建。
- 其他安装引用、未知角色/版本、并发操作和任意检查失败时，不删除未知资源。
- 数据卷和外部 PostgreSQL 保留；资料生成身份不变且完整时不重导。
- 构建/加载/就绪失败不伪造成功或旧二进制回退；计划不删除既有部署镜像或容器。
- 首次安装、重复安装和 upgrade 均交付配套 ZIP；固定加载目录逐文件等于 ZIP 白名单内容，非默认本机端口一致。
- ZIP、校验和、解压目录篡改与身份不配套必须失败；提交后恢复保持相同验证，未完成不得签发 ready。
